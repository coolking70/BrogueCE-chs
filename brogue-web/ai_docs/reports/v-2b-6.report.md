## 1. §1 四处 CE 机制的落地位置与行号

### 1.1 `keyMatchesLocation` — CE `Items.c:4036-4049` → `Game.ts`（私有方法 `keyMatchesLocation`）

三判据逐字直译（缺一不可）：

| CE | web | 位置 |
|---|---|---|
| `theItem->flags & ITEM_IS_KEY` | `theItem.category !== ItemCategory.KEY → false`（`ITEM_IS_KEY = Fl(13)`，Rogue.h:1374） | `Game.ts` 钥匙三件套块 |
| `theItem->originDepth == rogue.depthLevel`（:4038） | `theItem.originDepth !== undefined && !== this.depth → false` | 同上 |
| 循环：`posEq(loc)` 或 `keyLoc[i].machine == pmapAt(loc)->machineNumber`（:4040/:4042） | `e.loc.x === x && e.loc.y === y` 或 `e.machine === (cell?.machineNumber ?? 0)` | 同上 |

- **循环终止条件 `(loc.x || machine)` 的哨兵形态**：CE 的 `keyLoc[KEY_ID_MAXIMUM=20]` 是固定数组、靠全零条目截断（Rogue.h:1398 `#define KEY_ID_MAXIMUM 20`）；web 的 `keyLoc` 是紧凑数组、无哨兵条目，逐条直读即等价（代码注释已注明）。
- **CE :4042 机器号比对不带 ≠0 守卫（0==0 退化形态）**：照抄。生产中一切 `TM_PROMOTES_WITH_KEY` 消费点（锁门/铁笼）都在机器内（machineNumber ≠ 0），退化形态不可达；单元测试的合成格按生产口径取非零机器号（`v_2b_6_keys` C1/C2/C5 注释）。
- **消费端替换**：原 `Game.ts` 解锁分支的 `inventory.items.find(i => i.category === KEY)`（任意钥匙开任意锁）已删除，改走 `keyInPackFor(newX, newY, cell)`。有钥匙但都不认锁时按 CE `LOCKED_DOOR` 描述列（Globals.c:331 "you search your pack but do not have a matching key"）给出区分消息（新增 i18n 键 `door.no_matching_key`）。

### 1.2 `keyLoc` 第三维 `disposableHere` — CE `Rogue.h:1391-1395` → `Item.ts` + 快照

- `Item.keyLoc: Array<{ loc, machine, disposableHere? }>`（B-4b 略去的第三维补齐）；新增 `Item.originDepth?: number`（Rogue.h:1422 `item->originDepth`）。
- 消费端：`Game.keyMatchingEntry`（CE `useKeyAt` Movement.c:636-656 的条目定位半边）——匹配条目带 `disposableHere` 才消耗钥匙；缺省 `true`（V-2b-6 前的绑定无该字段，行为与旧 web"恒消耗"一致）。
- 快照：`GameSnapshotItem.keyLoc` 带 `disposableHere`、新增 `originDepth`，`serializeItem`/`deserializeItem` 往返；旧存档无键 → `originDepth === undefined` 按"当层"处理（登记偏差，见 §10）。

### 1.3 `keyInPackFor` / `keyOnTileAt` — CE `Items.c:4051-4087` → `Game.ts`

- `keyInPackFor(x, y, cell)`：背包版，解锁分支消费。
- `keyOnTileAt`：CE 的另一个消费者是 `TM_PROMOTES_WITHOUT_KEY`（Items.c:5067）——本轮数据无载体，web 只落背包版；接口未写成"只服务解锁"的形态（`keyMatchesLocation` 独立可复用）。注意 CE `keyOnTileAt` 还查**地上物品**与**怪物 carriedItem**（:4072/:4080）——地上形态的等价物是 `F1` 的地上钥匙匹配（解锁判定用背包版 + 生成期绑定，登记差异见 §10）。

### 1.4 `MF_SKELETON_KEY`（Rogue.h:2614 `Fl(29)`）

- CE 定义与消费：`Architect.c:1526` `addMachineNumberToKey(theItem, machineNumber, MF_KEY_DISPOSABLE)`——**机器条目**使钥匙开本机器任意锁（machineNumber 匹配，不绑坐标）。
- web 落地：`BlueprintEngine` KEY 绑定块——`fFlags.has('MF_SKELETON_KEY')` 时在 `keyLoc` 追加 `{ loc: {0,0}, machine: machineNum, disposableHere }`。10 号 Kennel 的 cage key 由此开整台机器的笼（`v_2b_6_keys` C4 正/反两钉）。
- CE `addLocationToKey`（:1523）对**一切 feature 物品**调用（非 KEY 物品带上 keyLoc 无语义）；web 只在 KEY 类上落——登记偏差（§10.2）。

## 2. §2 怪物携带 + `spawnBlueprintItem` KEY 分支怎么解开的

### 2.1 怪物携带（CE Architect.c:1622-1626 / :1705-1710 + Monsters.c:147-152）

- `Monster.carriedItem?: Item | null`（Monster.ts 新字段）。
- 指令链：feature 带 `MF_MONSTER_TAKE_ITEM` 时，`theItem` 在摘链前记入 `carryItem`（每 instance 覆盖、CE torch/torchBearer 字面）；feature 建完后**只挂到最后一只**携带者指令上（`carryIndicesPerFeature`，CE :1705-1710 字面）；`MachineMonsterSpawn.carriedItem` 下传，Game 消费点实化物品（`originDepth = depth`，Monsters.c:150 同证）。
- 死亡掉落：`playerTurnEnded` 的死亡清扫在 filter 前结算——物品落怪原地（CE `makeMonsterDropItem` Monsters.c:4075-4083 的"择邻格"用"落怪原地"近似：怪站的格必然可通行；物品落位守卫 `isPathingBlocker` 照抄，掉不进岩浆/深渊/墙）。近似登记偏差见 §10.2。
- 快照缺口：`GameSnapshotMonster` 未序列化 `carriedItem`（本轮无生产数据载体——Vampire lair 不在池，字段只在生成期存活；登记 §10.4，激活轮补）。

### 2.2 `spawnBlueprintItem` KEY 分支解锁（防"钥匙 ×2"回流）

B-4b 的困局：KEY feature 一律不发 → 补偿循环（每锁一把）顶上；解开 KEY 分支会让 16 号（门与钥匙**同一个 feature**，CE GlobalsBrogue.c:300）拿到两把钥匙。

本轮按 CE 数据不变量重整为三态：

| 形态 | CE 依据 | web 行为 |
|---|---|---|
| KEY feature 带 `MF_OUTSOURCE_ITEM_TO_MACHINE` | CE 一切领养钥匙（10/16/27/30-40 号） | BlueprintEngine 生成带 `keyLoc` 绑定的指令 → 领养子机器消费 → **落地**（指令带 `viaAdoption` 标记）；`generatedKey` 置位 → 该机器**跳过**补偿钥匙 |
| KEY feature 带 `MF_MONSTER_TAKE_ITEM` | CE 11 号 Vampire lair | 物品改挂怪物指令，不落 itemSpawns；`generatedKey` 置位 |
| KEY feature 无外包（web 自创：key_rat_trap 室内钥匙） | **CE 无此形态** | 指令继续被消费端跳过（B-4b 原判：躺在本机锁门内=死货）；`generatedKey` **不**置位 → 补偿钥匙照常供给 |

- 领养机器选择补一条 CE 数据不变量过滤（`buildAMachine`）：携带 `adoptiveItem` 时候选蓝图必须有 `MF_ADOPT_ITEM` feature。**根因**：CE 全部 BP_ADOPT_ITEM 蓝图都带领养 feature，web 的 key_rat_trap 是唯一没有的——seed424242/D3 实测它被抽中领养后钥匙**静默丢弃**（锁无钥匙死局，正是任务书 §0 说的"把局做死"）；按 D2 口径退池留形（改动申报见 §8）。
- `spawnBlueprintItem` 的无 id KEY 分支保留 `return null`（CE 类别级 KEY 走 chooseKind 的路径在 web 无消费者——16/10 号都走 id 分支）。
- `arcana.json` 新增 `cage_key`（CE "cage key"，Globals.c:1573，`excludeFromGeneration: true`）；16 号 feature 补 `itemId: 'iron_key'`（CE itemKind `KEY_DOOR` = "door key"，Globals.c:1572 ≙ web 既有 iron_key，名称沿用登记）。

## 3. §3 判断题：`ALTAR_INERT` 不独立成 TerrainType（别名保留）

**结论：继续用通用 `ALTAR` 作别名，27 号数据不动。**

CE 依据：**CE 根本没有"独立的普通祭坛 tile"**——`Globals.c:362` 的 `/*ALTAR_INERT*/` 就是 CE 的通用祭坛本体（flags `T_OBSTRUCTS_SURFACE_EFFECTS`、mechFlags `TM_LIST_IN_SIDEBAR | TM_VISUALLY_DISTINCT`、promoteType 0、CANDLE_LIGHT），机器 35 号（:401）用的就是它。CE 祭坛族的其它成员（ALTAR_KEYHOLE :363、ALTAR_CAGE_* :364/:365/:368、ALTAR_SWITCH :366、COMMUTATION/RESURRECTION_ALTAR :532/:538）各自是**独立 tile**，且 V-2b-4 已把那七条逐字落成 web 独立 TerrainType。

web 侧核对：`TerrainCatalog.ts` 的 `[TerrainType.ALTAR]` 条目注释自 V-2b-4 起就写着"CE ALTAR_INERT，Globals.c:362"，七字段（flags/mechFlags/ign/fireType/discoverType/promoteType/glowLight）与 CE 行逐一相等（DRAW_PRIORITY 17 = CE 第 4 列原值）。

因此任务书预设的分裂（"同一个 CE tile 在两条蓝图里落成两种 web 地形"）**不存在**：35 号落 `ALTAR` 与 27 号（key_secret_room，V-2b-1 落的也是 `ALTAR`）是同一个 TerrainType。反过来说，若把 `ALTAR_INERT` 独立成新枚举，才会制造出两个逐字段相同的枚举成员。

## 4. §6 可解性证明结果（合并前置条件）

实现：`src/test/v_2b_6_keys.test.ts` F 组（确定性地锭，非统计抽样）。

### F1 端到端锁-钥匙可达性（6 seed × D1-D26 = 156 层）

对每层每一把 LOCKED_DOOR：
1. **匹配性**：存在一把同层钥匙（category KEY、`originDepth === 当前层`）使 `keyMatchesLocation(lock)` 成立（坐标或机器号）；
2. **锁格可达**：锁格在玩家入口的可达分量内（泛洪口径：硬墙/岩浆/深渊/HOLE/PORTCULLIS_CLOSED 不可穿越；LOCKED_DOOR/MONSTER_CAGE_CLOSED 拿钥匙即开、SECRET_DOOR 搜索可开、BARRICADE 可燃）；
3. **钥匙格可达**：匹配钥匙所在格同分量。

结果：**6 seed × 156 层全绿**（`layersWithLocks ≥ 5` 的覆盖门也过）。诊断记录：初版口径把 SECRET_DOOR 列为不可穿越，seed777/D25 报了一处"锁不可达"——复核后确认该锁位于密门之后（CE 搜索可开），属口径过严而非死局；放宽后全绿。

### F2 Kennel 形态（§6.2：笼中盟友的钥匙）

16 seed × D1-D26 全量扫描，对每台 Kennel（以 `MONSTER_CAGE_CLOSED` 格的 machineNumber 识别）：
- 笼群机器必有 cage key（`keyLoc` 带该机器号的机器条目）——**否定面**：`RV2` 反向验证（§5）注入"删除机器条目"后该断言翻红（seed4/D13 实测）；
- `disposableHere === true`（CE :251 `MF_KEY_DISPOSABLE`）;
- 至少一把 cage key 在可达分量内（钥匙不会落进机器封闭区/熔岩——领养机器选址口径由 C-8/P1-33 既有守卫保证）。

### §6.3 `disposableHere=false` 不被前一把锁吃掉

F3 单元口径钉收口：匹配条目 `disposableHere: false` 时 `keyMatchingEntry` 返回该条目、解锁判据 `entry?.disposableHere ?? true === false` 不触发消耗。数据面登记：当前全部 KEY feature 都带 `MF_KEY_DISPOSABLE`（CE 原表如此，GlobalsBrogue.c:250/251/300 逐条核对），生产路径结构性无 `false` 载体——引擎收口由 F3 把守，数据载体留待 CE 有此形态的蓝图落地时行使。

### 怪物携带形态（§6.2 的另一半）

本轮入池数据**无** `MF_MONSTER_TAKE_ITEM` 载体（CE 11 号 Vampire lair 不在 web 池），该形态当前不可能死局（结构性空集）；引擎行为由 D1/D2 单元钉死（掉落、守卫），激活轮（Vampire lair 入池）按任务书口径需复跑 F 组。

### "有没有把局做死"的结论

- 修复了一个**本轮引入前就存在的真死局**：key_rat_trap 被抽中领养后静默丢弃父机器钥匙（§2.2，seed424242/D3 实测 2 锁 0-1 钥匙）——CE 数据不变量过滤后该形态不再出现。
- Kennel 的 cage key 经领养链落地（CE 同款），`MF_KEY_DISPOSABLE` 用后即毁——与 CE 一致，多笼共享一把钥匙由机器号匹配覆盖（CE 字面）。
- 未发现"CE 也如此"的死局复现（CE 兜底 `MF_KEY_DISPOSABLE` 的设计意图即"开完即毁、避免错钥匙积累"；web 现已同构）。

## 7. §7 两条对抗性要求的回答
