## 3. `PORTCULLIS_CLOSED` 可通行性的判断与 CE 行号

任务书把它列为"判断题"（"关闭的闸门该不该可通行？"）。**回 CE 查证后：它其实不是判断题。**

`BrogueCE-master/src/brogue/Globals.c:339`：

```c
/*PORTCULLIS_CLOSED*/  {G_PORTCULLIS, &gray, &floorBackColor, 10, 0, DF_PLAIN_FIRE, 0, DF_OPEN_PORTCULLIS, 0, NO_LIGHT,
    (T_OBSTRUCTS_PASSABILITY | T_OBSTRUCTS_ITEMS),
    (TM_STAND_IN_TILE | TM_VANISHES_UPON_PROMOTION | TM_IS_WIRED | TM_LIST_IN_SIDEBAR | TM_VISUALLY_DISTINCT | TM_CONNECTS_LEVEL), …}
```

**flags 第 11 列明写 `T_OBSTRUCTS_PASSABILITY`——关闭的铁闸就是挡通行。**

而"升起的闸门"是**另一张 tile**：`Globals.c:340` 的 `PORTCULLIS_DORMANT`，
其 flags 列为 `(0)`（可通行）、`promoteType = DF_ACTIVATE_PORTCULLIS`。
web 尚未迁移 `PORTCULLIS_DORMANT`，所以"升起"这一半目前由 `DF_OPEN_PORTCULLIS`
的 tile 缺口登记（`DF_MISSING_TILES`）承载。

因此：

- web 现有条目（`TerrainCatalog.ts` 的 `T_OBSTRUCTS_PASSABILITY | T_OBSTRUCTS_ITEMS`）
  **与 CE 逐位一致，不需要动**；
- 它进 `POST_LEGACY_TILES` 跳过集，只是因为它诞生于 C-4a 之后、**没有"旧硬编码判据"**
  可比（同 B-3 的 `FORCEFIELD` 族、V-2b-2b 的 `STATUE_INERT` 族）；
- 我另加了一条**正向**断言把这个判定钉死，并对另外五条**不该挡通行**的 wired 载体
  做反向钉死：

```
V-2b-3：wired 载体九条的通行判定 = CE 查表口径（四条墙族挡通行、五条可走）
  PORTCULLIS_CLOSED / WORM_TUNNEL_OUTER_WALL / WALL_LEVER_HIDDEN / PILOT_LIGHT_DORMANT → terrainAllowsMove=false、canMoveTo=false
  MACHINE_GLYPH / GAS_TRAP_PARALYSIS / GAS_TRAP_PARALYSIS_HIDDEN / MACHINE_PARALYSIS_VENT_HIDDEN / MACHINE_METHANE_VENT_HIDDEN → 均为 true
```

**这不是"挑一个能过的答案"，而是 CE 字面事实**：18/22 号蓝图的堵门体必须真的挡住玩家，
否则蓝图本身无解。反向验证见 §7-RV4。

## 5. C 类：真诊断（2 条）——本轮最重要的一节

### C1 `v_2b_2b_blueprints.test.ts` T6 第二条 —— `TM_IS_WIRED` 豁免

**报错**：`TM_IS_WIRED 格保留机器标记（CE :1695）: expected +0 to be 12`。

#### 诊断过程

1. **读原始断言**：夹具在机器内部**预置**一块 `PRESSURE_PLATE`，断言它作为"wired 格"
   被 `BP_NO_INTERIOR_FLAG` 的 `TM_IS_WIRED` 豁免保留机器标记，期望值 =
   `result.machineNumber`（本次运行 = 12）。
2. **实测**：该格 `machineNumber` 是 **0**。
3. **定位成因**：wired 分支的清除逻辑不在 `Promotion.ts`，而是 V-2b-3 在
   `BlueprintEngine.ts:924-933` 新增的 CE `Architect.c:1238-1243` 直译：机器标记块先
   无条件把内部既有的 `TM_IS_WIRED | TM_IS_CIRCUIT_BREAKER` 层清成 `FLOOR/NOTHING`。
   预置的 `PRESSURE_PLATE` 层被清掉 → 到 `:1694` 时该格**已不带** `TM_IS_WIRED`
   → 不获豁免 → 标记归零。**实测与推演一致**（我另外确认了该分支确实在 feature 落位**之前**）。
4. **回 CE 复核（关键）**：`BrogueCE-master/src/brogue/Architect.c`

   ```c
   1228:     machineNumber = ++rogue.machineNumber;
   1229:     for(int i=0; i<DCOLS; i++) {
   1230:         for(int j=0; j<DROWS; j++) {
   1231:             if (p->interior[i][j]) {
   1232:                 pmap[i][j].flags |= ((bp flags & BP_ROOM) ? IS_IN_ROOM_MACHINE : IS_IN_AREA_MACHINE);
   1233:                 pmap[i][j].machineNumber = machineNumber;
   1235:                 if (pmap[i][j].layers[DUNGEON] == SECRET_DOOR) { pmap[i][j].layers[DUNGEON] = DOOR; }
   1238:                 // Clear wired tiles in case we stole them from another machine.
   1239:                 for (int layer = 0; layer < NUMBER_TERRAIN_LAYERS; layer++) {
   1240:                     if (tileCatalog[pmap[i][j].layers[layer]].mechFlags & (TM_IS_WIRED | TM_IS_CIRCUIT_BREAKER)) {
   1241:                         pmap[i][j].layers[layer] = (layer == DUNGEON ? FLOOR : NOTHING);
   1242:                     }
   1243:                 }
   ```

   而 `BP_NO_INTERIOR_FLAG` 的清理在 **:1690-1702**（远在 feature 循环的 :1486-1488 之后）：

   ```c
   1690:    // Clear out the interior flag for all non-wired cells, if requested.
   1691:    if (blueprintCatalog[bp].flags & BP_NO_INTERIOR_FLAG) {
   1694:                if (pmap[i][j].machineNumber == machineNumber
   1695:                    && !cellHasTMFlag((pos){ i, j }, (TM_IS_WIRED | TM_IS_CIRCUIT_BREAKER))) {
   1697:                    pmap[i][j].flags &= ~IS_IN_MACHINE;
   1698:                    pmap[i][j].machineNumber = 0;
   ```

   **结论：CE 里"机器吞并前就在格上的旧板"同样保不住标记。** 顺序是
   `:1238-1243 剪线` → `:1486-1488 feature 落位` → `:1690-1702 摘标记`。
   旧夹具恰好把载体放在了"剪线之前"，于是它测的根本不是 `:1694` 的豁免。

#### 结论

**实现无缺陷。** web 的现状（标记 0）是 CE 的忠实结果；旧断言的期望值 12 才是那个
过期前提的产物。任务书要求"若结论是实现有缺陷，修实现而不是改断言"——**诊断结论是
断言错**，因此改断言（并保留原意）。

#### 处置（按留痕反转纪律，两半事实都钉死）

把该 `it` 改为 `TM_IS_WIRED 豁免（CE :1694）——已按 V-2b-3 反转：预置 wired 格先被剪线，
feature 自带载体才受豁免`：

- **(a)** 预置旧板 → 先剪线（地形回 `FLOOR`）→ 不获豁免 → 标记归零；
- **(b)** 蓝图**自己的** wired 载体（用 `MF_BUILD_AT_ORIGIN` 把 `GAS_TRAP_PARALYSIS`
  落在 origin，经 feature 在 :1238-1243 **之后**落位）→ **获豁免 → 保留标记**。
  这一半正是原断言想守的东西，仍然守着。

两条互为越界守卫，**都做过反向验证**（§7-RV1 / RV2）。

### C2 `p1_37_machine_flag_i18n.test.ts` AD3 —— 机器旗标穿存档往返

**报错**：`读档后 machineCells 未从网格重建: expected 45 to be 44`。

#### 诊断过程

1. **读断言**：`expect(machineCells.size).toBe(expectCount)`，
   其中 `expectCount = |∪ mr.cells|`（各机器 `MachineResult.cells` 的并集）。
2. **找那一格**（临时诊断脚本，用完已删）：`seed424242/D3`，多出的格是 **(25,23)**，
   `machineNumber = 5` → 机器 5 = `vestibule_flammable_barricade`（前厅机器，
   `cells` 只有 1 格 = origin）。它的**焚化药水**经 `MF_BUILD_ANYWHERE_ON_LEVEL`
   落在 interior 之外，被 `BlueprintEngine.ts:1181` 标了机器号。
3. **回 CE 复核**：`Architect.c:1484-1488`

   ```c
   1486:  // Mark the feature location as part of the machine, in case it is not already inside of it.
   1487:  pmap[featX][featY].flags |= ((BP_ROOM) ? IS_IN_ROOM_MACHINE : IS_IN_AREA_MACHINE);
   1488:  pmap[featX][featY].machineNumber = machineNumber;
   ```

   **CE 只打 pmap 旗标，不进 `p->interior`。** 也就是说 CE 里
   "机器标记格集" ≠ "机器 interior 集"，web 的
   `网格 machineNumber≠0` ≠ `∪ mr.cells`，**完全对应**。
4. **量化这个口径有多脆**（临时诊断，5 seed × D1-D26 全扫）：
   **130 层里 31 层有机器，其中 25 层 `A ≠ B`**（A = 网格派生集，B = ∪mr.cells），
   **双向都差**：
   - `A − B > 0`：CE :1486 的 interior 外 feature 落位（如 424242/D3 差 1；
     999/D15 差 6；777/D15 差 5）；
   - `B − A` 也可以很大：`777/D26` 是 `A=29, B=143`（差 114）——那是
     `BP_NO_INTERIOR_FLAG`（CE :1690-1702）事后把非 wired 格的 `machineNumber`
     清回 0，于是 B 里的格反而不在 A 里。

   ⇒ **原断言只在"该层首台机器既无 interior 外 feature 落位、也无 NO_INTERIOR_FLAG"
   这种偶然层上成立**（同 project_conventions 记的 B-4a"挑 seed 的测试"一族，
   是**假的信心**）。V-2b-3 的六条新蓝图移动了 RNG 流，把这颗走运的骰子挪开了，
   于是它在 `seed424242/D3` 上露出原形。

#### 结论

**不是真回归，也不是"新地形带来的合理计数变化"——是断言的参照系从一开始就错了。**
`loadSnapshot` 重建 `machineCells` 的口径是**扫网格**（`Game.ts:7973-7979`：
`if (cell && cell.machineNumber !== 0) this.machineCells.add(...)`），
所以判据只能是同口径的网格派生集，不能是 `∪ mr.cells`。实现无缺陷。

#### 处置

把参照系换成与 `loadSnapshot` 同口径的**网格派生集**，并**保持全等**（不放宽）：

```ts
expect(machineCells.size, '读档后 machineCells 未从网格重建…').toBe(gridDerived.size);
for (const k of gridDerived) expect(machineCells.has(k), …).toBe(true);   // 逐元素
for (const k of machineCells) expect(gridDerived.has(k), …).toBe(true);   // 反向也查
```

并加一条**越界守卫 + 事实钉死**：`A − B` 的格必须**恰是机器自己的布点**
（`mr.center` ∪ `itemSpawns[].pos` ∪ `monsterSpawns[].pos`），且本层实测值恰好是
`['25,23']`（坐标钉死，失败消息写明"机器构成变动时请回 CE 重核该层"）。
原有的逐格"快照/读档后 `machineNumber ≠ 0`"断言一字未动。

> 顺带登记（**只列不修**）：生成期 `Game.populateLevel:1132-1135` 的 `machineCells`
> 是**从 `mr.cells` 构造**的，读档后却是**从网格重建**的——同一个字段两处口径不一致，
> 且**生成期那一侧比 CE 弱**（CE 的 `IS_IN_MACHINE` 住在 pmap 上，包含 :1486 的
> interior 外 feature 格）。这是真实的 CE 平价缺口，但改它要动 `Game.ts`（不在本轮
> 授权清单）且会移动内容落位、需重捕获基线，故本轮**只登记不动手**。见 §9-④。

## 6. D 类：基线偏离的成因拆分

### 6.1 重捕获结果

`generation_baseline` 从 **234 处偏离** → 重捕获后绿（4 seed × D1-26，逐层
`fp` / `n` / `species` / `items` 四字段）。固件 note 已写明本轮重捕获理由与拆分。
固件结构未变（`note` / `seeds`[4] / `levels`[4 seed × 26 层]，566 行 → 643 行）。

### 6.2 成因拆分：**234 = 100% 新蓝图入池，通电机制 0，可完全分开**

任务书说"分不开就说分不开，不要编"。**这里分得开**，用两组受控实验 + 一次直接计数：

| 组 | 构造 | 相对 V-2b-2b 基线的偏离 |
|---|---|---|
| ① 现状态 | 六条新蓝图入池 + 通电机制代码全在位 | **234 处**（fp 64 / n 57 / species 62 / items 51） |
| ② 对照 | 把六条新蓝图**从抽签池剔除**（运行时按 id 过滤 `this.blueprints`），**通电机制代码一字未动** | **0 处** |
| ③ 直接计数 | 生成期 `activateMachine` 调用次数 | **0 次** |

结论链：

- ② = 0 ⇒ **六条新蓝图是唯一的偏离源**；剔除它们后逐位回到 V-2b-2b 基线，
  说明"通电机制 + 九条新地形 + 14 条新 DF 目录条目 + 剪线步"**在生成期零影响**。
- ③ = 0 ⇒ 与 ② 相互印证。`activateMachine` 只由**交互期**驱动
  （`runPromotionUpdate` / `promoteOnStep` / `promoteOnItemPickup` / `promoteOnItemPlaced`），
  生成期一次都不会跑到；它那两次 shuffles（CE `Time.c:1177-1180`）是生成基线能看见
  RNG 位移的唯一途径，而它根本没被执行。
- 所以 **234 处 = 100% 来自新蓝图入池（抽签池总频率与命中序列改变），
  0 来自通电机制**。两股成因**不重叠**，无需按层相加。

### 6.3 对原始规格 §4 的回应（**与预设不符，见 §9-③**）

`v-2b-3.prompt.md` §4 写："若生成期零触发 → 基线**不应**偏离。偏离了就是实现误伤，
停下来查，别用重捕获盖过去。"

实测：**生成期零触发，但基线偏离 234 处**。按 §4 的字面，这会被判成"实现误伤"。
但 §4 的前提漏了一件事：**本轮要落地的六条蓝图本身就会改变抽签池**
（总频率 +32，且 `randRange(1, totalFreq)` 的滚动映射整体平移），
与"通电机制是否触发"无关。§4 只考虑了 `activateMachine` 的洗牌这一条 RNG 通路。

我没有停在"误伤"上，也没有直接盖过去，而是做了 ②/③ 两组测量把两股成因**分开**：
偏离**全部**是六条蓝图（本轮的交付物、属有意变更），通电机制贡献**恰好 0**
（§4 真正担心的那件事，实测不成立）。因此按 finish 提示词 D 类的指示重捕获，
并把拆分写进固件 note。

> 另一条侧证：② 组在**保留剪线步**的前提下仍得 0 偏离，说明
> `BlueprintEngine.ts:924-933` 的剪线在 4 seed × 26 层内没有改动任何一层的四个记录字段

## 9. 与预设不符之处（**只列不修**；含提示词本身的错误）

### ① 提示词把 vitest 的省略号计数当成了数组长度 —— **数字错**

`v-2b-3-finish.prompt.md` §1 A 类第一行写
`c_4a_0_layer_model 归属表与 drawPriority 表 59 vs 50`。
实测输出是：

```
AssertionError: expected { '0': +0, '1': +0, '2': +0, …(59) } to deeply equal { '0': +0, '1': +0, '2': +0, …(50) }
```

`…(59)` 是 vitest 的"**另有 59 项**"（前面已显示 3 项），不是总数。
真实数字是 **62 vs 53**（3+59 vs 3+50）。同一份清单里
`c_4a_terrain_catalog 全 TerrainType 键覆盖 62 vs 53` 写对了，可见是这一行的读法问题。
本报告按 **62 vs 53** 处理（§2-A1）。

### ② WIP 产物里的 CE 行号引用有偏移 —— **注释错，不影响行为**

`Architect.c:1244-1250`。**实测是 `:1238-1243`**（`:1244` 是 `if (p->interior…)` 的右花括号）。

**实测是 `:1271-1286`**（`:1273` 是条件表达式的第二行续行）。
两处都是**引用偏移，不是逻辑错**（代码本身与 CE 逐字一致，已逐行核对）。
按"边界外的只列不动手"惯例：`BlueprintEngine.ts` 是生产文件、`v_2b_3_wired.test.ts`
