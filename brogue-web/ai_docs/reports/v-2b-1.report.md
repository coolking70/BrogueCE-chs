## 1. 六件事逐条落地情况与 CE 依据

### 1.1 personalSpace 边长 2r+1 → 2r−1

- 改动：`BlueprintEngine.ts` `markPersonalSpace`，循环范围 `-radius..radius` → `-(radius-1)..(radius-1)`。
- CE 依据：`Architect.c:1462-1471`，循环 `featX - personalSpace + 1 .. featX + personalSpace - 1`（边长 2ps−1）；CE 自己的注释（`:1459-1461`）："0 means nothing gets cleared, 1 means only the tile itself, and 2 means the 3x3 grid centered on it"。
- 行为核验：ps=2 由 5×5−1=24 收紧为 3×3−1=8（+中心=9，与 CE 一致）；ps=1 新公式只触及中心格，中心已由 applyBlueprint 主循环（改前 778 行）无条件 `usedCells.add(pos)` 加入，净效果"只清自身"，与 CE 一致；ps=0 由调用点 `personalSpace > 0` 守卫短路，且新公式下 `-(−1)..(−1)` 自然为空，双保险。

**§6 复核 1（中心格等价性）——证实**：`markPersonalSpace` 只在同一实例循环内、`pos` 非空（`if (!pos) break` 在先）之后被调用，且 `usedCells.add(pos)` 无条件先于它；不存在"markPersonalSpace 执行而中心未入 usedCells"的路径。CE 在同一循环里把中心一并置 occupied，两边等价。任务书引用的行号（778）与实际（改前 778）吻合。

### 1.2 `MF_NEAR_ORIGIN` 距离基准 center → origin

- 改动：`findFeaturePosition` 的 NEAR_ORIGIN 分支曼哈顿距离基准从 `center` 改为第 3 参 `origin`（=BP_ROOM 机器的门位格 / 前厅机器的落位锚点）；`center` 形参就此失去全部读者，**连带删除**（连同调用点实参），否则 `npm run build` 的 `noUnusedParameters` 会红。
- CE 依据：`Architect.c:1257` `calculateDistances(distanceMap, originX, originY, …)`（距离图以 origin 为源）；`:1336-1341` MF_NEAR_ORIGIN / MF_FAR_FROM_ORIGIN 的 distance25/75 界；`:1343-1349` IN_VIEW_OF_ORIGIN 系直接 `getFOVMask(…, originX, originY, …)`；候选函数 `cellIsFeatureCandidate`（`:490-497`）签名只收 originX/Y——**ORIGIN 系旗标无一以 center 为基准**。
- 已知留形（登记）：web 仍用曼哈顿距离近似 CE 的"路径距离 25 分位界"，本次只改基准点、未改近似方式（任务书口径即如此）。
- 影响面：当前生产数据中带 MF_NEAR_ORIGIN 的活跃 feature 只有 `reward_library` 的 SIGN（area_shrine 两处属 thematic 退池，绝不建造）。对 BP_ROOM 机器这是行为变化；前厅机器 center==origin 不受影响。

## 2. §2.2 必答题：27 号的祭坛会不会进 altarGroup？

**不会进组。** 证据链：

1. `altarGroupId` 的**唯一写入点**是 `BlueprintEngine.applyBlueprint` 的 `MF_ALTAR_GROUP` 分支（BlueprintEngine.ts:810-816）：feature 带 `MF_ALTAR_GROUP` 才分配组号并写到格子。
2. `Architect.ts:382-394`（原 381-392）只是**下游收集器**：把 `mr.altarGroupId !== null` 的机器里的 ALTAR 格收进 `architect.altars`——它不产生组，只搬运组。
3. 塌陷的触发守卫在 `Game.ts:3234`：`if (groupId !== null)`——组号为 null 时整段跳过。
4. CE 27 号的 ALTAR_INERT feature 旗标是 `(MF_ADOPT_ITEM | MF_TREAT_AS_BLOCKING | MF_NOT_IN_HALLWAY)`（GlobalsBrogue.c:358），**无 MF_ALTAR_GROUP**；逐字落地后该祭坛格的 `altarGroupId` 恒为 null。

**结论：本项无风险**——玩家取走（未来落在）祭坛上的物品不会触发 web 自创的塌陷语义；27 的祭坛也不会进 `architect.altars` 的组登记。**登记给 V-2b-4**（风险 1 的正式处置轮）。

**附加发现（登记给 V-2b-6 钥匙轮）**：27 号领养来的 KEY 物品指令**在消费端被跳过**——`Game.populateLevel` 消费 itemSpawns 时 `if (spawn.category === 'KEY') continue;`（B-4b 建立的"钥匙总量恒等于锁数"哨兵）。所以 27 号祭坛上**不会有可见物品**，玩家实际拿到的钥匙由 `needsKey` 锁具从牌堆发放（与 key_rat_trap 的室内钥匙同款处置）。CE 的"钥匙躺在密室祭坛上"在 web 的钥匙真实化（V-2b-6）之前无法逐字呈现，这是已知近似，不是本轮引入的缺陷。

## 6. 与预设不符之处 / 边界外发现（只列不修）

a. **`LoopMap.CE_CHOKE_COUNT_CAP = 41` 需要上调（LoopMap.ts 不在授权清单，未动）**。c2 守卫的原前提"所有窗口上沿 ≤ 40"被 27 号打破后，封顶的决策等价性改为如下口径（已写进 c2 注释）：真值 ≤40 照旧精确；真值 ≥41 的割点报 41，窗口上沿 ≥41 时仍是候选（CE 对真值 41-100 也收，等价；对真值 >100 则 web 多收——CE 会拒）。多收部分的危害被 `gateSealsOnlyInterior` 兜住大半（把世界封成两半的窄点因"误封非机器格"被否决，孤立 dead-end 大口袋才幸存）；且洪泛早停使 visited 集只含 ≤42 格，`mapMachineInterior` 的内部扩展对封顶门位自然封顶在 ~42 格。**残余偏差**：真值 42..100 的口袋 web 取 ~42 格前缀（CE 取整个口袋）；真值 >100 的孤立口袋门位 web 会收（CE 拒）。正解是把 cap 上调至 ≥101，属 LoopMap.ts 的改动，**留给验收方授权**。
b. **27 号祭坛上没有可见物品**（§2 附加发现）：领养 KEY 指令被消费端 B-4b 哨兵跳过，钥匙走锁具牌堆。任务书说"MF_ADOPT_ITEM 引擎已消费"没错（指令确实被领养并推入 itemSpawns），但消费端 KEY 跳过使其不可见——任务书未提这一层。归 V-2b-6。
