## 0. 结论摘要

1. **真正的卡点不是 65 个地形符号，而是四套缺失的引擎机制加一个 schema 缺口**：
   - **M1 wired 机器触发网络**（CE `TM_IS_WIRED` + `promoteTile`/`activateMachine` 供电传播 + 断路器 + 触发源：拾取/踩踏/钥匙，Time.c:1173-1284）——web 为零。这是 40+ 条蓝图的总闸。
   - **M3 DF（dungeon feature）系统**（CE `dungeonFeatureCatalog` + `spawnDungeonFeature` blob 铺装，Globals.c:603 起）——web 完全没有（P1-23 已登记），**且 web `FeatureDef` 连 df 列都没有**，CE 蓝图 feature 行的第 1 列在 web schema 里无处安放。约 24 条蓝图连"逐字表达"都做不到。
   - **M2 休眠唤醒**（`MF_MONSTERS_DORMANT` + `DFF_ACTIVATE_DORMANT_MONSTER`，石像/ turret / 墙内怪破壳而出）——web 无近似物；`DungeonFeatureCatalog.ts:42` 只有旗标登记。
   - **M5 钥匙系统真实化**——比 V-2a 登记的更松：web 解锁**不读 keyLoc**（`Game.ts:3194-3198` 任意钥匙开任意锁），`spawnBlueprintItem('KEY')` **无条件返回 null**（`Game.ts:964-972`），钥匙种类只有 iron_key。CE 的 `keyMatchesLocation` 双键匹配（坐标 + machine 号，Items.c:4036-4049）在 web 没有执行点。
   - **M8 怪物携带物品**——web `Monster` 无 `carriedItem` 字段（`Appearance.ts:148-153` 明文记载），小偷/守卫/BOSS 持钥匙全部落不了地。
2. **粗测纠错**：怪物侧 14 个"缺口"**全部不成立**（缺了一层 CE monsterCatalog 名称映射）；「仅 6 条无需新载体即可落地」**偏乐观**，真实数字是 **3 条**（16 Plain locked door / 17 Plain secret door / 27 Secret room）——但偏乐观的方向不在地形载体，而在机制（DF schema、autoGenerator 接线、守卫真实持有）。
3. **拆轮**：建议 9 轮（见 §2.3），每轮解锁 3/6/7/7/7/4/13/8/15 条，合计 70 条 + 1 条 CE 自带 freq=0 的禁用蓝图（数据照落、零投入）。

## 1. 对粗测的逐项纠正

粗测（任务书 §1）是脚本抽取的符号差集。本轮用同样的抽取口径复现了它的地形部分，**完全吻合**；怪物部分和落地判定两部分有系统性错误。

### 1.1 复现吻合的部分（可直接采信）

- CE 71 条、web 20 条（reward 5 / vestibule 4 / key_guard 7 / thematic 4）✓。
- CE 蓝图引用的地形符号去重 **77 个**，其中 web `TerrainType` 已有 **12 个**（DOOR×6 / SECRET_DOOR×6 / FOLIAGE×4 / WALL / GRASS / CHASM / LAVA / SACRED_GLYPH / CRYSTAL_WALL / LOCKED_DOOR / FLOOR / GRANITE），**缺口 65 个** ✓。
- 缺口 top 排名逐条吻合：ALTAR_SWITCH 14、STATUE_INERT 13、ALTAR_INERT 10、CARPET 9、MACHINE_GLYPH 7、MACHINE_TRIGGER_FLOOR 5、PEDESTAL / TORCH_WALL / WALL_LEVER_HIDDEN 各 4 ✓（按"解锁蓝图数"口径，即含该符号的蓝图条数）。
- 88 ≈ 65 地形 + 14 怪物（伪缺口）+ ~9 物品种类 id（KEY_CAGE/KEY_PORTAL/KEY_DOOR/SCROLL_ENCHANTING/POTION_LIFE/POTION_LEVITATION/POTION_FIRE_IMMUNITY/POTION_DESCENT/POTION_LICHEN）。精确复现 88 无从做起（粗测脚本不在场），但构成对得上。

### 1.2 纠正一：14 个怪物"缺口"全部不成立（粗测偏悲观）

粗测把 CE 的 `MK_*` 符号直接对 web `monsters.json` 的 snake_case id 比，漏掉了 CE `monsterCatalog`（Globals.c:1025）的名称映射层。逐个核验（`Rogue.h` monsterTypes 枚举序 ↔ Globals.c:1025 目录序 ↔ web id）：

| CE 符号 | CE 目录名 | web id | 判定 |
|---|---|---|---|
| MK_GUARDIAN（5 蓝图） | stone guardian | `stone_guardian` | **已有（别名）** |
| MK_WINGED_GUARDIAN（4） | winged guardian | `winged_guardian` | **已有（别名）** |
| MK_SENTINEL（3） | sentinel | `sentinel` | **已有（别名）** |
| MK_UNDERWORM（3） | underworm | `underworm` | **已有（别名）** |
| MK_GOBLIN_CHIEFTAN（2） | goblin warlord | `goblin_warlord` | **已有（别名）** |
| MK_MIRRORED_TOTEM（2） | mirrored totem | `mirrored_totem` | **已有（别名）** |
| MK_VAMPIRE / MK_WARDEN_OF_YENDOR / MK_RAT / MK_SPIDER / MK_ELDRITCH_TOTEM / MK_SPARK_TURRET / MK_ZOMBIE / MK_PHANTOM | 同名 | 同名 id（Warden_of_Yendor 大小写不同） | **已有（别名）** |

且 web 已把 CE 的"机器专属怪不自然刷出"对齐了：monsters.json 16 条 `machineOnly:true`（stone_guardian / winged_guardian / sentinel / Warden_of_Yendor / mirrored_totem / eldritch_totem 等）在 `Game.ts:977/1254` 排除出普通刷怪，与 CE `HORDE_MACHINE_ONLY`（Rogue.h:2049-2055）同义。**怪物载体不是本轮的任何一块拦路石**；需要验收的只是这些怪的行为参数（不在本轮范围，见 §5 风险 6）。

### 1.3 纠正二：「仅 6 条无需新载体」偏乐观，真实数字 3 条（粗测偏乐观）

任务书 §5 猜粗测"很可能偏悲观（把命名差异算成了缺口）"——方向猜反了。命名差异（怪物侧）确实算成了缺口，但那 6 条"无需新载体"里 **4 条在机制侧过不去**：

| 粗测判定 | 本轮判定 | 差在哪一步 |
|---|---|---|
| Outsourced item 可落地 | **不可** | 无地形载体没错，但它的全部产出经 `MF_OUTSOURCE_ITEM_TO_MACHINE` 交给收养机器；web 收养链路虽在（BlueprintEngine.ts:827-830），**收养方没有 `MF_ADOPT_ITEM` feature，物品指令被静默丢弃**（V-2a §9.1a 实证）；CE 逐字落表=一台产不出任何东西却消耗奖励房配额的机器 |
| Plain secret door 可落地 | **可** ✓ | 无异议：SECRET_DOOR 载体已有，前厅分支（fillVestibuleInterior）+ P1-42 搜索揭示已具备 |
| Idyll / Swamp 可落地 | **不可（逐字口径）** | 两者的 feature 全部是 DF 列驱动（DF_GRASS / DF_DEEP_WATER_POOL / DF_SWAMP）；web `FeatureDef` **没有 df 列**、没有 spawnDungeonFeature——数据无处安放。若降级为"web 近似替身"可跑，但 V-2 链的口径是"不近似模拟"（roadmap:189） |
| Camp / Dismal 可落地 | **不可（逐字口径）** | 同上：DF_HAY/JUNK/URINE/VOMIT/AMBIENT_BLOOD/ASH/BONES 全是 DF 列（Dismal 的 ASH tile web 虽已有，但铺装机制缺） |

另有一批粗测没发现的"现在就能落地"：**16 Plain locked door、27 Secret room**。前者 terrain 全齐（LOCKED_DOOR 已有）、递归外壳已在生产跑（web vestibule_locked 就是它的近似版），CE 逐字落表即可跑（钥匙语义暂时由锁驱动近似兜底）；后者的 `ALTAR_INERT` 用 web `ALTAR` 作别名即可、`MF_ADOPT_ITEM` 引擎已消费——它是唯一一条收养链路真正闭环的 CE 蓝图。

**权威结论：CE 逐字口径下今天能落地 3 条（16 / 17 / 27），不是 6 条。**

### 1.4 纠正三：几处命名/计数校正

- **`MACHINE_GLYPH` 不是 `SACRED_GLYPH` 的别名**（任务书 §1 猜测"很可能只是命名不同"）。CE 自己同时有两者：SACRED_GLYPH（Globals.c:479，T_SACRED 安全区圣徽，web 已有）与 MACHINE_GLYPH（Globals.c:404，`TM_IS_WIRED|TM_PROMOTES_ON_PLAYER_ENTRY` 的机器触发符文，踩上即激活供电）——行为完全不同，`MACHINE_GLYPH` 是**真缺口（机制级）**。
- 祭坛族是 **10 种**变体不是 8 种（任务书 §1 说"八种祭坛变体"）：ALTAR_INERT / ALTAR_SWITCH / ALTAR_SWITCH_RETRACTING / ALTAR_CAGE_OPEN / ALTAR_CAGE_RETRACTABLE / ALTAR_KEYHOLE / COMMUTATION_ALTAR / RESURRECTION_ALTAR / AMULET_SWITCH / SACRIFICE_ALTAR_DORMANT。
- **web 的 ALTAR 不是纯装饰**：它有 web 自创的"取物塌陷"语义（`Game.ts:3232-3257`，从某祭坛取走物品 → 同 altarGroupId 的其余祭坛塌成 CHARRED_FLOOR 并销毁其上物品）。CE 祭坛没有这个行为；扩表落祭坛族时这个自创语义必须同轮裁决（见 §5 风险 1）。
- **V-2a 报告 §9.1a 的"CE 16 条 BP_ADOPT_ITEM 蓝图"实为 32 条**（KEY HOLDERS 一节 32/32 全带 `BP_ADOPT_ITEM`，且 32/32 带 `MF_ADOPT_ITEM` 消费 feature；脚本复核）。"web 7 条 key_guard 一条都没有"成立。结论不变（独立成轮），数量翻倍意味着该轮的解锁面比 V-2a 估计的大一倍。
- **CE 前厅是 10 条不是 9 条**（V-2a §9.1b；GlobalsBrogue.c:298-343）。
- **71 条里有 1 条自带 freq=0 禁用**：Summoning circle（:495-498，注释 `// DISABLED. (Not fun enough.)`）。落表时照抄 freq 0，零机制投入，不占拆轮额度。
- 粗测清单里的解析噪音（BLUEPRINTS/FEATURES/MACHINES/ROOMS/HOLDERS/FLAVOR/REWARD/DISABLED/LIQUID/DUNGEON/SURFACE/DEEPEST_LEVEL/AMULET_LEVEL）本轮按 tileType 枚举成员过滤，已全部剔除。

## 2.3 拆轮建议

拆法原则沿用 V-1c 先例：**同一机制闭环不可拆**（wired 网络的传播/触发源/断路器三件同轮），**能独立验证的必拆**（每轮都有独立的生成基线重捕获与验收面）。以下 9 轮按依赖序，解锁数合计 70 + 48 号禁用条。

### V-2b-1 地基与奠基轮（解锁 3：16/17/27）

## 3. §3 四条前情的处置建议

### 3.1 BP_ADOPT_ITEM 守卫持有（V-2a §9.1a）

**成立，且比登记的更大**：CE 带 BP_ADOPT_ITEM 的蓝图是 **32 条**（V-2a 写 16 条），32/32 带 MF_ADOPT_ITEM。独立成轮 = 本方案 V-2b-6。web 侧三处地基缺陷（keyLoc 不读、KEY 物品生成 null、无 carriedItem）已在 §0.1 列明。27 号 Secret room 是现成的领养链路闭环样本，V-2b-1 落表后即可作为该轮的回归锚。

### 3.2 personalSpace 语义偏差（V-2a §9.5）

**该修，放 V-2b-1**。理由：CE 蓝图数据按 CE 口径（personalSpace=r 清 (2r-1)² 含心格）设计落位密度；带着 web 口径铺 71 条，每条 feature 的 personalSpace 值都要做一次口径折算、且之后永远背着这个换算。V-2a"统一修法会移动全部机器布局"的顾虑在 V-2b 本来就是既成事实（全表重写=全部布局重摆=重捕获），搭车修的边际成本最低。

### 3.3 自创旗标整体替换（V-1b 审计表）

替换目标按 roadmap:82-102 已核对的 CE 表达：
- `MF_FILL_DOORWAY`（vestibule_flammable 1 处）→ CE 原样：`WOODEN_BARRICADE + MF_PERMIT_BLOCKING|MF_BUILD_AT_ORIGIN`（GlobalsBrogue.c:311）——即 V-2b-2 落 19 号蓝图本体。
- `MF_RING`（key_lava_moat 1 处）→ CE 原样：`LAVA {60,60} LIQUID + MF_REPEAT_UNTIL_NO_PROGRESS` + `DF_LAVA_RETRACTABLE`（:424-425）——REPEAT 归 V-2b-2，DF 归 V-2b-7，38 号蓝图本体落在 V-2b-9。
- `MF_SCATTER`（7 处、8 条蓝图）→ 按场景三分：铺满=MF_EVERYWHERE；液体=MF_REPEAT_UNTIL_NO_PROGRESS；散布=大 instanceCount+personalSpace。
**执行轮次**：旗标字符串的删除与现存 8 条自创蓝图的改写/退池必须在 V-2b-1 完成（引擎本就不认这三个旗标，删了零行为变化；但 V-2b-2 起新数据按 CE 语义写，留着旧串会误导逐字对账）。引擎侧的新语义分别在 2/3/7 轮到位。

### 3.4 两处 V-2a 登记（SESSION_HANDOFF 队列 13）

## 4. 验收方还没意识到的风险

1. **web ALTAR 的自创塌陷语义与 CE 祭坛族正面冲突**。`Game.ts:3232-3257`：从祭坛取物→同组祭坛塌陷+销毁其上物品。CE 无此机制（commutation altar 的事件是换魔）。V-2b-4 落 10 种 CE 祭坛时若沿用 web ALTAR 作 ALTAR_INERT 替身，玩家取收养物品会触发自创塌陷、直接毁掉 CE 的机器语义。替身策略必须与塌陷语义同轮裁决，**这条不在任何前情登记里**。
2. **"任意钥匙开任意锁"比 V-2a 登记的更松**。V-2a §9.6 只登记了 keyLoc kind 第三维缺失；实际消费侧（`Game.ts:3194-3198`）根本不读 keyLoc，任何 KEY 都开任何锁。扩表后蓝图带三种钥匙 kind（cage/door/portal），不修匹配，钥匙系统是摆设。已在 V-2b-6 范围内，但验收方对现状严重度的认知需要校准。
3. **重模拟测试的时长账单会滚雪球**。V-2a §9.4 已登记 armor_model_effect 越过 360s timeout；V-2b 每轮都加数据、都重捕获基线，生成期 RNG 消耗只增不减。**建议 V-2b-1 就处理该测试的 timeout/分层策略**，否则第 3 轮起门禁会先于内容坏掉。
4. **CE 有 1 条自带禁用蓝图**（48 Summoning circle，freq=0）。粗测与任务书都没提。照落数据、零投入；别把它算进任何一轮的解锁数，也别"顺手修好它"——CE 注释明言 Not fun enough。
5. **护符来源双轨冲突**。web 在 D26 由 populateLevel 直接投放护符（Game.ts:1204-1216）；CE 的护符房是机器（MT_AMULET_AREA → BP_ADOPT_ITEM 机器）。V-2b-4 落 15 号（AMULET_SWITCH 机器）或 V-2b-8 接 MT_AMULET_AREA 时，两套来源会叠加出两个护符。需要一次性裁决（建议：机器接管，populateLevel 直投退位），登记为 V-2b-4 的必答题。
6. **怪物行为参数未验**。本轮只验了"怪物 id 存在"，没验 stone_guardian/warden 等的行为参数与 CE 一致（P1-7 伤害记法还在队列）。V-2b-5 扩守卫池前建议抽查一次，否则机器造出的守卫可能拿着 web 旧数值。
7. **19 号 barricade 房有 50% 概率不可解**。CE 蓝图给两个 ALTERNATIVE 点火物：INCENDIARY_DART 与 POTION_INCINERATION。web 飞镖"有数据、投掷点燃未接"——ALTERNATIVE 掷骰选到飞镖的那一半房会没有点火手段。落 19 号前必须接飞镖点燃（或临时改单选药水并登记偏差）。
8. **`minimumInstanceCount` 全表显式化是 V-1c 挂账**（BlueprintEngine.ts:33-41 注释"全表显式化归 V-2b"）。V-2b-1 落新三条时就要按 CE 原值显式给，别等最后一轮——否则新旧数据缺省口径不一致，min 检查行为分叉。
