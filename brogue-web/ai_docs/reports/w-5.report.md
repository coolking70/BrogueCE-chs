# W-5：法器实例生成模型

基准提交：`9f007e8`。本轮只处理既有法器的生成初始值与实例持久化；W-0 §2.3 为规格。开始时工作树无预存修改。未提交代码。

## 1. CE 依据与实现

- `BrogueCE-master/src/brogue/Items.c:323–347`：staff 初始次数从 2 开始，第一次 50% 加 1；成功后才抽 15%，再成功后才循环抽 10%。`enchant1 = charges`。故 P(E=2)=50%、P(E=3)=42.5%、P(E=4)=6.75%、P(E=5)=0.675%，尾部无硬截断。
- 新 `src/engine/Items/ArcanaInstance.ts` 的 `rollStaffEnchantment` 保留条件抽数顺序。`ItemLoader.spawnStaff` 在新建时分别写 `enchantment=E`、`maxCharges=E`、`charges=E`，三者是独立字段。
- `variants/GlobalsBrogue.c:702–710` 的既有五种 wand range：teleportation 3–5、slowness 2–5、beckoning 2–4、invisibility 3–5、empowerment 1–1，clump 全为 1。`Items.c:347 → Math.c:34–56` 对接已有 `randClumpedRange`；初始次数另存为 wand 的兼容容量，供现存 UI/生命周期读取。
- `Math.c:41–43` 和 web `Random.randClumpedRange` 都对单值区间直接返回。因此 empowerment 的零抽数来自源码与 10000 次实际调用计数守卫，并非“样本没生成所以认为零足迹”。其 frequency=3 的既有错误仍留 W-24。
- 三条自创退池项不变：fire/lightning wand 直造固定 2，light staff 直造固定 4；light 的 E 初始化为其容量 4。不伪造 CE 身份，不纳入随机池。
- 测试覆盖边界 49/50、14/15、9/10、条件短路及 E>5；另用固定 RNG 跑 50000 次 staff 分布与每种 wand 10000 次次数/端点/实际抽数。没有用本轮地牢样本中未出现的尾部值推断实现不会生成它。

## 3. 持久化、迁移与 E 分离

`Item.arcanaInstanceVersion?:1` / `GameSnapshotItem.arcanaInstanceVersion?:1` 区分新实例与旧档。保存显式写版本、原有 E/容量/当前次数；反序列化用 `restoreArcanaInstance`，不调用 spawn。

- 有版本：E、容量、次数原样回放；包括 E=0，也不会擅自用容量覆盖。
- 无版本的 staff：E 取原档 `maxCharges`；缺容量才查旧 JSON 的固定容量，再缺则1。剩余次数独立保留，0 仍是0；缺次数才按原容量给满值。
- 无版本的 wand：保留原附魔字段和剩余次数；容量缺失按旧 JSON 固定容量兜底，绝不重新抽 range。
- 迁移后的实例写版本1，重复存读幂等。`timesUsed`、未知态、充能计数器仍沿原快照路径。

测试把 `rng.randRange/randPercent/randClumpedRange`、`spawnStaff/spawnWand` 全部换成抛错函数后，实际 `Game.deserializeItem` 仍能迁移 2/3/4/8 容量的满/半/空电旧档，以及目录兜底。迁移前后 `JSON.stringify(rng)` 全等，覆盖 substantive/cosmetic 两套内部状态与计数器，而非只看返回值。完整 JSON → loadSnapshot 验证地上/背包两出口与重复加载。

范围区分：整个既有 `loadSnapshot` 会重新播种并调用 `initConsumables` 洗 cosmetic 风味；它在本轮以前就存在。这里证明**新增实例迁移路径零抽数**，没有声称全局读档行为从来不操作 RNG。

E 与次数分离的行为证据：E3 初始3次，实际 Enter 提交后当前次数2、E仍3、容量仍3；JSON存读后 `[2/3]` 不变。Playwright 整页截图 `w-5-evidence/inventory.png` 已打开复核，浏览器状态/零页面及控制台错误见 browser.json。技能客户端的 canvas 导出黑图只登记为导出问题，没有用它充当视觉通过。
