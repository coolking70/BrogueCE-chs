## 2. `MF_GENERATE_HORDE` 的 CE 依据与落地

**CE 依据**：`Rogue.h:2590`（`MF_GENERATE_HORDE = Fl(5)`，"generate a monster horde that has all of the horde flags"）；消费点 `Architect.c:1591-1599`：

```c
if (feature->flags & MF_GENERATE_HORDE) {
    monst = spawnHorde(0, (pos){ featX, featY },
                       ((HORDE_IS_SUMMONED | HORDE_LEADER_CAPTIVE) & ~(feature->hordeFlags)),
                       feature->hordeFlags);
    if (monst) monst->bookkeepingFlags |= MB_JUST_SUMMONED;
}
```

与 `monsterID` 分支（:1601-1612，单只、只看列值非零）并列且在其**之前**。`hordeFlags` 列 = `machineFeature.hordeFlags`（Rogue.h:2629 一带）。

web 落地：

- `BlueprintEngine.ts`：`FeatureDef.hordeFlags?: string[]`（数据列）+ `applyBlueprint` 的 MF_GENERATE_HORDE 分支（生成指令，CE 的 forbidden/required 拆法逐字照抄）；
- `Game.ts` `spawnHordeAtFeature()`：forbidden = `(IS_SUMMONED|LEADER_CAPTIVE) & ~hordeFlags`（CE :1594 字面——feature 自己要求的旗标从禁用集除名）、required = `hordeFlags`（CE pickHordeType Monsters.c:511 的 requiredFlags 半边：horde 必须全部带上）、OOD 掷骰照常（Monsters.c:794-804 在 spawnHorde 内部，机器 horde 同样适用）、落点即 feature 落点 + spawnsIn 地形核（CE :812-828，failsafe 50；**50 次耗尽后 CE 照样落下最后一次抽中的 horde**——`while (--failsafe && tryAgain)` 退出时不再复核，照抄）；领袖与成员都收进 `collected`（CE spawnMinions :743 成员也置 MB_JUST_SUMMONED），逐只走 `finalizeBlueprintMonster`（睡姿/休眠/记属机）；
- `spawnHordeAt` 加了**可选**第 6 参 `collected?: Monster[]`（缺省 undefined，既有调用方行为逐位不变）；
- `SPAWNS_IN_TERRAIN` 补 `STATUE_DORMANT` / `TURRET_DORMANT` 两个映射（CE hordeCatalog 的 statue/turret 族 `spawnsIn` 列；普通铺怪池被 HORDE_MACHINE_ONLY 排除，该映射只被机器 horde 路径行使）。

顺带核对：CE 本版的 `machineFeatureFlags` 里**没有** `MF_GENERATE_MONSTER`（枚举 Fl(7) 注释 "unused"）；`monsterID` 的结构体注释虽写 "if MF_GENERATE_MONSTER is set"，但代码路径只看列值——与 web V-2b-3 的处置一致，未改动。

## 4. §4 四股基线成因的分离结果

**方法**（沿用前两轮受控单变量）：以"蓝图池"为单因素做归离实验——把 `blueprints.json` 换回 HEAD（V-2b-4 版，39 条），**其余全部改动保留**（休眠子系统 / horde 接线 / 新地形目录 / machineHome / 快照改动），按基线同口径（4 seed × D1-D26 指纹/怪物数/物种/物品数）采样，与 V-2b-4 基线逐层比对。

**结果：0 处差异。**

| 成因 | 分离结果 |
|---|---|
| ① 休眠接线改变既有 reward_statuary 行为（§1.4） | **零独立效应**：web 的 reward_statuary = CE 15 号，frequency=0（CE 原值），`blueprintQualifies` 的频率加权抽签结构性选不中它（roll 减 0 永不命中）。v_2b_4 E1 已实测"6 seed × D1-D26 建成 0 台"。接线后它同样从未建成 → 生成流无感。任务书 §1.4 预告的"既有蓝图行为改变"**在 web 实际不会发生**（除非未来有人把 15 号频率调正） |
| ② MF_GENERATE_HORDE 接线 | **零独立效应**：旧池 39 条蓝图零载体；该分支只有新蓝图的 feature 能触发 |
| ③ 八条新蓝图入池 | **漂移的唯一有效来源**（与④合并，见下） |
| ④ 新地形落地 | 与③**不可分离**：七条地形在 web 无 autoGenerator 路径，只随蓝图 feature 落格；蓝图池换回旧版后它们零落格（Exp B 指纹与旧基线逐位一致即为证） |

结论（如实）：**四股在生成流层面收敛为一股有效成因——③+④**；①②是"接上但没有载体可服务"的接线（对抗性要求一的反向确认：我专门验证过"如果它们有独立效应我会看到 ExpB 偏离旧基线——没有看到"）。RNG 流移动：**是**，由③蓝图抽签/feature 落位/horde 抽取的消耗序列变化引起；`generation_baseline.json` 已按最后状态重采，note 里写明了成因归离与本段。
