# U05a：领养/携带产物唯一性

基准 `4d90ed4`（含 U01 `552c25b`），2026-09-24。权威：X-0 §4.1、§4.2 U05a、§3.1 K30，以及本树 CE 源码。完成指令身份、互斥归属、整机收口、普通怪物/horde 交接与回滚守卫；未修改物品目录、蓝图、生成池、ItemLoader 或快照格式。

## 1. CE 所有权执行路径及线索复核

源码：[Architect.c](../../../BrogueCE-master/src/brogue/Architect.c)。

1. `1494–1519`：有 `MF_GENERATE_ITEM` 或有待领养品且 BP/feature 均允许领养，才进入物品块。领养直接取同一指针，并将局部 `adoptiveItem=NULL`，只能一次。只有自产物进入 `spawnedItems[]`；领养品的释放责任仍由生成它的祖先登记表持有。
2. `1504–1516`：自产物经 generateItem/质量重掷后登记，失败统一删除。Q 族和 STAFF/WAND 实化属于 U05，本轮没有搬入。
3. `1521–1531`：写 item flags、钥匙位置/机器绑定与 originDepth；只有既非 OUTSOURCE 又非 TAKE 才 `placeItemAt`。
4. `1534–1587`：外包至子机器，最多十次；每次先摘地面/背包链，再试同一个指针。成功合并子机器的自产物/怪物登记，最后清空 `theItem`，不再交给本机怪物。子失败时领养品不在子自产登记中；重试前的摘链以及祖先最终释放共同保证安全。不能简单说“子失败会删除父物品”。
5. `1589–1627`：horde 返回领袖；显式 monsterID 若同格有怪，会替换。**只有 `monst && theItem && TAKE` 同时满足才覆盖 torch/torchBearer**。范围是整台机器，非每个 feature；后续无物品的实例不清空配对。一次领养的多实例合成例中，首个成功领养者保持携带，并非无条件交给最后生成的怪。
6. `1704–1710`：整机成功后，删除最终携带者原携带物、将 torch 从地面摘链、交给该怪。这里的“删旧品”指最终携带者已有的品，不是每次循环删除上一把 torch。
7. `470–490`：abort 从地面/背包摘物，先清怪物对相同物品的引用再删除物品，最后清怪；`1577–1583`、`1680–1687` 恢复地图并 abort，子孙登记已经并入祖先。

任务线索的生成/登记/三种去向、一次领养、祖先回滚均成立；“每实例覆盖”“最后一只怪”需以上条件限定。K30 的“双实化”对普通携带怪成立；对 horde，原 Game 的 `continue` 根本不消费 carriedItem，实际是多一条地面指令、携带者拿不到物品，不能统一称为两实体重复。

## 2. web 根因、模型与事务

仅修改两个生产文件：

- [BlueprintEngine.ts](../../src/engine/Generator/BlueprintEngine.ts)：`MachineItemSpawn.instanceId` = 当前层 machineNumber + 本机创建序号，不消耗 RNG 或实体 ID。`generatedItems` 是创建登记，**不是额外生成指令**；外包后源登记保留，子机器新位置指令继承同一 instanceId，全部类别、种类、资格和 keyLoc 元数据随之保留。领养不登记新创建。
- 地面、子机器、怪物三种去向共用排他判断；外包成功清 `theItem`。torch 配对只在确有物品和怪物指令时更新，整机完工后提交一次。不会因无物品的后续 feature/instance 清空先前配对。
- 发布结果前递归检查：每个创建 ID 恰一去向；传入的有 ID 领养品恰一去向；无重复所有者。失败返回 null，由既有 `buildAMachine → backupLevel/restoreLevel` 收口，不发布父子产物。
- [Game.ts](../../src/engine/Core/Game.ts)：完整扁平事务先验重复 ID；按身份缓存唯一实化结果（含显式 null），统一 originDepth/keyLoc 投影。普通怪物和 horde 领袖共用 handOff；horde helper 返回 `collected[0]`，即生产 spawnHordeAt 先登记的领袖。旧携带物替换后不另发地面/背包副本。
- 生成 ID 的生命周期仅是当层延迟事务；实体实化后仍用 Item.id，U01 的序列化/两阶段恢复合同未变。optional 字段只兼容既有合成指令夹具，生产创建均有 ID；不是旧存档兼容。

**防御边界**：当前 CE 目录不存在“同机连续自产多把 TAKE torch”或 TAKE 自产物却无怪的有效行。CE 字面循环对前者会只提交末次配对，早先生成品留在登记但无归属。web 对这种合成/损坏事务返回失败，避免发布幽灵；没有改目录去掩盖它。51 个新测试中包含这两个拒绝面。

## 4. 递归失败与替换对抗

- 子机器已领养并产生携带怪，再强制失败：每次恢复子备份，十次全败传递到父，外层九次尝试共 90 次子失败。最终 null；整层四层地形/机器号/陷阱/不可挖标记/pendingItems/pendingMonsters 全等；父物品输入逐字不变。
- 子机器成功，父随后 feature 最小实例数失败：九次父尝试均撤回子产物，最终 null；同样比较完整 backupLevel，而非只查 items.length。
- 失败后再次成功领养同一输入，输出仅一个原 ID；无失败指令残留。原 V-1c 的递归结构、深扁平化、配额、原子回滚测试全部纳入最终回归。
- 一次领养 + 三个同 feature 怪 + 后续 feature：仅第一次同时具备 item/monster 的配对携带，后续无物品者不擦除它。
- ADOPT + OUTSOURCE + TAKE 合成冲突：只能去子机器；本机地面和怪物均无第二份。
- Game 接到同 ID 同时在地上和怪身的坏指令，实化前报错；horde 领袖先有另一物品时，交接替换原品，旧品不进入任何地面/怪身/背包表。
