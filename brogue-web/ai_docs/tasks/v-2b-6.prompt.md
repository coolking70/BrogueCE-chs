# V-2b-6 钥匙系统真实化 + 怪物携带物品

## 0. 本轮的分量

这轮碰的是**唯一一个能把关卡做成死局的子系统**。web 现在「任意钥匙开任意锁」，
所以玩家永远卡不死；一旦按 CE 做成「钥匙认锁」，**拿错钥匙、钥匙被消耗在错误的锁上、
或者携带钥匙的怪被杀在够不着的地方，都可能让这一层再也打不通**。

所以本轮的验收重点不是「落了几条蓝图」，而是**「有没有把局做死」**。任务书里为此埋了
§6 的强制项，先读完再动手。

解锁 4 条 + 1 条语义收口：

| # | CE 名 | 缺的载体 | 关键旗标 |
|---|---|---|---|
| 8 | Outsourced item | **无** | 纯领养链路（web `MF_ADOPT_ITEM` 已有） |
| 10 | Kennel（笼中盟友） | `KEY_CAGE`、`MONSTER_CAGE_CLOSED`、`DF_AMBIENT_BLOOD`、`DF_BONES` | `MF_KEY_DISPOSABLE`、**`MF_SKELETON_KEY`** |
| 16 | Plain locked door | `KEY_DOOR` | `MF_KEY_DISPOSABLE` |
| 35 | Pit traps（钥匙版） | `ALTAR_INERT`（见 §3 的判断题） | `MF_ADOPT_ITEM` |
| 40 | Poison gas | `MACHINE_POISON_GAS_VENT_HIDDEN`、`PORTCULLIS_DORMANT`、`WALL_LEVER_HIDDEN_DORMANT` | `MF_ADOPT_ITEM` |

`POTION_DESCENT` / `SCROLL_TELEPORT`（40 号引用）**web 都已有**
（`potion_of_descent` / `scroll_of_teleport`），不用新增。

**16 号是「语义收口」不是新增**：web 现有的 `vestibule_locked` 就是它的近似版
（V-2b-1 按 CE :298-300 逐字落过），本轮把 `KEY_DOOR` 载体补上、让钥匙真的认这把锁。

## 1. 钥匙真实化（M5）——CE 四处

### 1.1 `keyMatchesLocation` — `Items.c:4036-4049`

```c
static boolean keyMatchesLocation(item *theItem, pos loc) {
    if ((theItem->flags & ITEM_IS_KEY)
        && theItem->originDepth == rogue.depthLevel) {
        for (int i=0; i < KEY_ID_MAXIMUM && (theItem->keyLoc[i].loc.x || theItem->keyLoc[i].machine); i++) {
            if (posEq(theItem->keyLoc[i].loc, loc)) return true;
            else if (theItem->keyLoc[i].machine == pmapAt(loc)->machineNumber) return true;
        }
    }
    return false;
}
```

三个判据缺一不可：**`originDepth == 当前深度`**（跨层带下去的钥匙不认锁）、
**坐标匹配**、**机器号匹配**（两者是「或」）。循环的终止条件
`(loc.x || machine)` 也要照抄——它是 keyLoc 数组的哨兵。

**web 已有一半**：`keyLoc?: Array<{loc, machine}>`（`Game.ts:203`，B-4b 建的）
并在 `Game.ts:1326` 填充。**缺的是消费端**：`Game.ts:3304` 的解锁判定写的是
`items.find(i => i.category === KEY)`——**任意钥匙开任意锁，完全不查 keyLoc**，
而且无条件消耗钥匙。

### 1.2 `keyLoc` 的第三维 `disposableHere` — `Rogue.h:1391-1395`

```c
typedef struct keyLocationProfile { pos loc; short machine; boolean disposableHere; } keyLocationProfile;
```

web 的结构体缺这一维。它决定**开完锁后钥匙消不消失**——`MF_KEY_DISPOSABLE`
（数据里已有 2 个载体、引擎零消费）就是写它的那个旗标。现在 web 无条件消耗，
等于对所有锁都当 disposable。

### 1.3 `keyInPackFor` / `keyOnTileAt` — `Items.c:4051` / `:4062`

按位置找包里/地上的对应钥匙。`keyOnTileAt` 还被 `TM_PROMOTES_WITHOUT_KEY`
用到（`:5067`）——那条不在本轮范围，但别把接口写成只服务解锁。

### 1.4 `MF_SKELETON_KEY`

10 号用它（万能钥匙，开本机器任意锁）。CE 依据自行定位并给行号。

## 2. 怪物携带物品（M8）

`Monster` 没有 `carriedItem` 字段（`Game.ts:3618` 的注释自己记着「web 无载体」）。
本轮补上，并接 `MF_MONSTER_TAKE_ITEM`：怪被杀时掉落所携物品。

10 号 Kennel 的盟友、以及 CE 的小偷类怪都依赖它。**注意**：如果携带钥匙的怪
能走到玩家够不着的地方（或掉进熔岩/深渊），就是死局——见 §6。

**另一个已登记的堵点**：`Game.spawnBlueprintItem` 的 `KEY` 分支**无条件返回 null**
（B-4b 起如此，V-2b-0 §1.3 登记）。10 号的 `KEY_CAGE` 要发钥匙，这条必须解开。
解开时注意别让 B-4b 当初要避免的「钥匙 ×2」回流——读那轮的报告。

## 3. 一道判断题：`ALTAR_INERT` 要不要独立成 TerrainType

V-2b-1 落 27 号时把 `ALTAR_INERT` 直接写成了 web 的通用 `ALTAR`（数据里就是 `"ALTAR"`）。
但 V-2b-4 之后 web 已经有了真正的祭坛族（`ALTAR_CAGE_OPEN` / `COMMUTATION_ALTAR` /
`RESURRECTION_ALTAR` 等各自独立）。

35 号又要用 `ALTAR_INERT`。**请判断**：继续用通用 `ALTAR` 作别名，还是让它独立成
TerrainType？判据是 CE 的 `ALTAR_INERT` 与 web `ALTAR` 在 tile 字段上有无行为差异
（不只是外观）。给出 CE 行号与结论；若结论是要独立，**同时把 27 号的数据一起改过来**
（不改就会出现「同一个 CE tile 在两条蓝图里落成两种 web 地形」的分裂）。

## 6. 强制项：可解性证明

**本轮必须证明「没有把局做死」，这是合并的前置条件。**

写一个端到端用例：**多 seed × D1-D26 全量生成，对每一层的每一把锁，证明存在一条
可达路径让玩家拿到能开它的钥匙。** 至少覆盖：

1. 钥匙在领养机器里（8/35/40 号形态）——玩家能进那台机器；
2. 钥匙由怪携带（10 号形态）——那只怪可达、且它的活动范围不会让钥匙落进
   不可达地形（熔岩/深渊/机器内部封闭区）；
3. `disposableHere=false` 的钥匙不会被前一把锁吃掉。

若某个形态**当前实现下确实可能死局**，**不要硬把用例写绿** ——
如实报告、给出复现 seed，并说明是「CE 也如此」还是「web 移植缺陷」。
CE 有它自己的兜底（例如 `MF_KEY_DISPOSABLE` 的设计意图），若 web 缺某条兜底，
那就是本轮的真发现。

## 7. 授权反驳 + 对抗性要求

事实判断若与 CE 不符，**驳回并纠正**并给行号。前几轮你在这条上抓出验收方多处错误
（CE 护符房不是抽签建成、`MF_EVERYWHERE` 的屏蔽是空转、`>= -10` 含等号），继续这样做。

**对抗性要求（沿用两条）**：
① 若出现「疑似断言过期」的诊断，回答「如果结论反过来是实现错，我会看到什么现象？
我确认过没看到吗？」
② 每条新断言回答「这条用例在什么实现缺陷下会翻红？」——**钥匙匹配尤其容易写成
自己证明自己**（造一把 keyLoc 指向 X 的钥匙、断言它能开 X）。真正的守卫是
**否定面**：keyLoc 指向 X 的钥匙**开不了** Y、跨层带下去的钥匙**不认**同坐标的锁。
