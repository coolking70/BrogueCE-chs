# 任务 P1-28：`behaviorFlags` 与 `abilities` 两套数据通道没打通

工作目录已是 `brogue-web/`。C 原版在 `../BrogueCE-master/src/brogue/`（唯一事实来源，**只读**）。

## 病灶（验收方探针实测）

`Monster` 上有两个互不相通的 `Set`：
- `behaviorFlags`（`Monster.ts:230`）—— 装 `MONST_*`，由 `monsters.json` 的 `behaviorFlags` 字段填充（`Monster.ts:309-310`），读取入口是 `hasBehavior()`
- `abilities` —— 另一套小写 id（`'flying'`、`'immune_fire'` 等）

**两者之间没有任何映射**（我 grep 确认：没有 `MONST_IMMUNE_TO_FIRE → abilities.add('immune_fire')` 这类转换）。

而 `Game.applyEnvironmentalEffects()` 里两处关键判定查的是 **`abilities`**：

```ts
// Game.ts:5541
const isFlying = entity.hasStatus('flying') || entity.hasStatus('levitating')
    || (entity.abilities && entity.abilities.has('flying'));

// Game.ts:5556（熔岩分支）
&& !(entity.abilities && entity.abilities.has('immune_fire'))
```

于是 `monsters.json` 里写在 `behaviorFlags` 的 `MONST_IMMUNE_TO_FIRE` / `MONST_FLIES` **完全不起作用**。

验收方实测（种子 20260916）：
```
[D] 火免 Wisp 在熔岩：hp=0     ← 应存活
```
Wisp 的数据是 `behaviorFlags: ['MONST_IMMUNE_TO_FIRE', 'MONST_FLIES', 'MONST_FLITS', 'MONST_NEVER_SLEEPS', 'MONST_FIERY', 'MONST_DIES_IF_NEGATED']`——**同时带火焰免疫和飞行两道豁免，却照样被烧死**。

对比：你在 P1-27 新加的那条豁免用对了通道（`entity.isInvulnerable()` 内部读 `hasBehavior('MONST_INVULNERABLE')`），旧的两条没跟上。

后果是玩家可见的：CE 里趟着岩浆走的火系生物（Wisp、flamedancer、salamander 之类）在 web 里会被岩浆烧死。

## 必做

1. **先做一次全仓排查**：grep 所有读 `abilities.has(...)` 的地方，逐个判断它是否本应读 `behaviorFlags`。把清单写进报告——**我只确认了 `applyEnvironmentalEffects` 这两处，别的地方很可能也有**，这是本轮的主要价值。
2. 修正判定，让 `behaviorFlags` 里的 `MONST_*` 真正生效。**具体方案由你定**（在读取处同时查两个 Set、或建一张映射表、或在构造时把 `MONST_*` 归一化进 `abilities`），但必须：
   - 不破坏 `abilities` 既有调用方；
   - 在报告里说明你为什么选这个方案，以及它对其它读取点的影响面。
3. 逐条核对 CE 语义再决定映射关系，**不要凭名字猜**：
   - `MONST_IMMUNE_TO_FIRE` ↔ 火焰免疫：CE 的消费点不止熔岩（`exposeCreatureToFire`、燃烧结算等），请查全。
   - `MONST_FLIES` / 悬浮：CE 里"飞行"与 `STATUS_LEVITATING` 是**两回事**，请读 CE 确认各自在熔岩/深水/陷阱处的作用，别混为一谈。
   - web 的深水现已不致死（P1-27），但 `canMoveTo` 仍排除深水——**本轮不要动它**（见路线图 P1-25，待验收方重新裁决）。
