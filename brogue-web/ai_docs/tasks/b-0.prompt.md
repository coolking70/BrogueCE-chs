## 一、为什么先测绘

Phase B 的余项（**鉴定系统 / 投掷武器 / 占位物品**）是当前路线图上
**最大的不确定性**，也是**玩家每一局都会碰到的核心循环**——
药水喝下去之前不知道是什么、卷轴读了才知道、戒指戴上才显形。

直接投"实现鉴定系统"会重蹈 C-4 的覆辙（那一轮预设了 web 不存在的底座，
投不出去）。F/G 链的经验是：**先测绘，产出对照表与基线，再据此拆轮**。

**本轮的产出是决策依据，不是代码。**

---

## 二、要测绘什么

### 1. CE 的鉴定系统全貌

自己从 CE 源码抠，我不给数据表（验收方在"照抄 CE 表格"上的错误率高于执行方，
这是 C-4a-0 那轮的教训）。线索：
- 物品的未知态如何表示、`ITEM_IDENTIFIED` 一类旗标；
- **随机化的风味名**（药水颜色、卷轴标题、戒指材质、魔杖木料）如何与真实种类绑定；
- `shuffleFlavors` 一类的洗牌时机与种子归属；
- 使用后的自动鉴定、`autoIdentify`、"猜名"（call）机制；
- 鉴定卷轴、以及"用过一次就知道"的部分鉴定；
- 诅咒物品的显形时机。

### 2. web 现状逐条对照

`src/engine/Items/`（或实际所在目录，自己定位）、`ItemLoader`、
`src/data/*.json` 的物品表。逐条回答：
- 哪些已实现、哪些是占位、哪些完全没有；
- **风味名系统 web 有没有**？（旧的 C 版 web 移植曾做过中文卷轴标题，
  但这是新的 JS 重构版，别假设它继承了任何东西）
- 未知态在存档里怎么表示（或根本没表示）；
- 物品生成池与鉴定状态的耦合点。

### 3. 投掷武器与占位物品

- CE 的投掷机制（飞刀/标枪/投掷斧的弹道、回收、命中）；
- web 现有 `throwCommand` 一类的入口到了哪一步；
- 路线图 P1-16 登记的"3 个占位卷轴"具体是哪三个、缺什么系统支撑。

### 4. ★ 载体盘点（本项目硬规矩）

对每一条 CE 机制，回答"**web 今天有没有东西会触发它**"。
没有载体的只登记不实现——`SESSION_HANDOFF.md`「这一轮做了会不会是空壳？」。
C-4c 的硫矿"每回合掷骰 11 次全部缓办"就是没盘点的下场。

### 5. ★ 行为基线测量（后续轮"逐位不变"门禁的依据）

仿 F-0 §4：给出**可复跑**的基线数字。至少：
- 多种子多层：各类物品的生成数量分布、已鉴定/未鉴定比例；
- 拾取、使用、丢弃的完整回合流水（状态快照）；
- 决定性复核（同种子同操作两遍全等）。

口径自己定但要写清楚，后续轮要用同一套复测。

### 6. 差异清单与拆轮建议

- CE 有而 web 没有 / web 有而 CE 没有（**D2 口径：自创内容保留代码但退出游戏**）/
  **两边都有但规则不同（最危险，重点列）**；
- 据此给出 **B-1…B-n 的拆轮建议**：各自动哪些文件、门禁是什么、
  哪些既有测试会翻红（**按交接文档的「两段 grep」法列**）。
- **若你认为应该先做投掷武器再做鉴定系统，或者拆法与我设想不同，直接反驳。**
