## 为什么这一项现在做

上一轮 C-0（`addLoops` 环路）已落地，但**收益被本轮卡住**。验收方实测：

```
每层实际开出的环路门：均 2.7 扇（最小 0、中位 3、最大 7）
seed 777 的 D1：再开候选 0 扇，IN_LOOP = 0%
同图对照：每多开 2.4 扇门，割点比例 5.5% → 4.4%（机制有效）
```

机制是有效的，但**没有多少地方能成环**——因为 web 的房间太少、走廊太少。
`addLoops` 的候选必须是"两侧都是地板、且绕行距离 > 20 的墙格"，房间稀疏就凑不出这种格局。

## CE 事实（已核实）

`carveDungeon()`（Architect.c:2456-2478）：

```c
theDP = dungeonProfileCatalog[DP_BASIC];
adjustDungeonProfileForDepth(&theDP);
theFirstRoomDP = dungeonProfileCatalog[DP_BASIC_FIRST_ROOM];
adjustDungeonFirstRoomProfileForDepth(&theFirstRoomDP);
designRandomRoom(grid, false, NULL, theFirstRoomDP.roomFrequencies);
attachRooms(grid, &theDP, 35, 35);          // ★ attempts=35, maxRoomCount=35
```

深度剖面（Architect.c:2425-2434），`descentPercent = clamp(100*(depth-1)/(amuletLevel-1), 0, 100)`：

```c
roomFrequencies[0] += 20 * (100 - descentPercent) / 100;   // 浅层偏好
roomFrequencies[1] += 10 * (100 - descentPercent) / 100;
roomFrequencies[3] +=  7 * (100 - descentPercent) / 100;
roomFrequencies[5] += 10 * descentPercent / 100;           // 深层偏好（洞穴）
corridorChance     += 80 * (100 - descentPercent) / 100;   // ★ 浅层走廊多，深层几乎没有
```

首房间（Architect.c:2436-2448）：**深度 1 恒为入口房**（其余频率清零，`roomFrequencies[7] = 1`）；此后 `roomFrequencies[6] += 50 * descentPercent / 100`。

**`dungeonProfileCatalog` 的基准值请自己查**（`DP_BASIC` / `DP_BASIC_FIRST_ROOM`），不要照抄验收方的转述。

## web 的现状（Architect.ts:39-44）

```ts
const dpBasic: DungeonProfile = {
    roomFrequencies: [2, 1, 1, 1, 7, 1, 0, 0],   // 硬编码；[6] 与 [7] 恒为 0
    corridorChance: 10                            // 恒定
};
this.attachRooms(dpBasic, 40, 15);                // CE 是 35, 35
```

三处偏差：
1. 频率表不随深度变化 → **全 26 层长得一个样**，深层不会变洞穴、浅层走廊不够多。
2. `roomFrequencies[6]` / `[7]` 恒为 0 → 两种房型（含入口房）**永不生成**。
3. `maxRoomCount` 是 15，CE 是 35 → **房间数只有 CE 的 43%**。

## 必做

1. `dungeonProfileCatalog` 的两个基准剖面照 CE 落数据。
2. `adjustDungeonProfileForDepth` / `adjustDungeonFirstRoomProfileForDepth` 照 CE 实现。
3. `attachRooms` 的 attempts / maxRoomCount 对齐 CE（35 / 35）。
4. 首房间按 CE：深度 1 恒入口房。
5. **房型齐全**：确认 web 的 8 种房型与 CE 的 `roomFrequencies` 下标一一对应。
   若 web 缺某几种房型的实现（例如下标 6、7 对应的），**如实报告缺哪些**，
   本轮只做能做的，缺的登记为后续轮次——**不要为了填满表格而临时造房型**。

## 必须实测汇报（本轮的验收核心）

1. **房间数**：改动前后，5 种子 × D1-D26 的每层房间数均值/分布。
2. **走廊占比随深度的变化**：浅层应显著多于深层（CE 的 `corridorChance` 从 90 降到 10）。
3. **房型分布随深度的变化**：浅层与深层的房型直方图应当明显不同。
4. **★ 环路收益**：`addLoops` 每层开出的门数、`IN_LOOP` 点亮比例，与 C-0 后的基线对比
   （C-0 后：门均 2.7 扇；IN_LOOP 5.9%/0%/17.1%/12.3%/30.5%）。**预期显著上升**；
   若没上升，如实报告并分析——那说明瓶颈不在房间数。
5. **深水总量**：与 C-0 后的每层均 12.7 格对比。
