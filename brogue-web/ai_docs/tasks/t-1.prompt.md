## 2. 四件事的细节

### 2.1 A：蓝图物品改走频率加权（P1-53）

`Game.ts:844` 的 `spawnBlueprintItem(category, id, x, y, depth)`：
当蓝图**给了具体 id** 时直接生成（:847-848，**保持不变**）；
当蓝图**只给类别**（`SCROLL` / `POTION` 等）时，web 现在是
`rng.randRange(0, pool.length - 1)` —— **等概率**（:857 及同族分支）。

CE 的 feature 类别物品走 `generateItem(category, -1)` → `chooseKind(table, count)`
—— **按 `itemTable.frequency` 加权**（`Items.c:409-420`）。
关键后果：`SCROLL_ENCHANTING` / `POTION_LIFE` / `POTION_STRENGTH`
在基表里 frequency 为 0（B-4a 已落地的计量表机制），
**等概率抽取会让它们照常被抽中，加权抽取则几乎不会**。

这正是 B-4b 拆掉两个结构性投放点后、附魔卷轴仍有 21-32/局
（CE 量级约 12-15）的主因。

**web 已有 `ItemLoader.chooseKind(frequencies)`**（`ItemLoader.ts:213`，
B-4a 从 `Items.c:409-420` 逐字移植）。本轮把无 id 分支改为调用它。

⚠️ **注意深度过滤与频率加权的交互**：web 现有分支先按
`depth >= minDepth && depth <= maxDepth` 过滤再等概率抽。
CE 的 `chooseKind` **不做深度过滤**（CE 的深度控制在别处）。
**这是本轮最容易抄歪的一处**：去 CE 查清 feature 物品到底有没有深度约束、
在哪一步施加，然后决定 web 是「先过滤再加权」还是「直接对全表加权」。
**把你的判断依据写进反驳节。** 不要默认沿用 web 现状，也不要默认照抄 CE 字面。

### 5.1 哨兵纪律

本轮移动生成流。新哨兵只许三种形态：① `rng.randomNumbersGenerated` 增量；
② `createHeadlessGame(seed,'test')` 完全隔离合成层（清怪清物后 reseed）；
③ 性质断言。**不许锚定 RNG 流绝对位置。**
撞见既有哨兵因位移而断，优先**改形态**；确实只能维护式 pin 的
（如 `c_5` 那条"恰等于一层生成成本"），在注释里写明为什么不能改形态。
