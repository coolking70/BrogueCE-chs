## 1. ⚠️ 本轮的核心风险：伤害不只走一个入口

W-0 原话"**不能只改 takeDamage 因为有直接 `hp -=`**"。
验收方粗扫了一下（**只作量级参考，请自行完整确认**）：
`engine/` 与 `entities/` 里有约 **10 处**直接 `hp -=` 一类的扣血，
分布在 `Core/Game.ts`、`entities/Player.ts`、`entities/Creature.ts`。

⇒ **护盾只装在主伤害入口上，其他路径的伤害会绕过去。**
要求：**逐个列出所有扣血点**，对每一处判定——
- 这类伤害在 CE 里**该不该被护盾吸收**？（"绕盾伤害"是 W-0 点名的一项）
- 若该吸收，**接进护盾**；若不该，**写明 CE 依据**

**不要**为了"统一"把所有直接扣血都改走 takeDamage——那可能改变它们的其他语义
（例如死亡结算顺序，W-10 刚做过"死亡只结算一次"）。

## 4. 教训（已连续二十二轮验证）

闭包走四条边；退池留形 = 加引擎过滤不改数据；覆盖门换样本不改期望；
**「建成 0 台」≠「RNG 足迹为 0」**；驳回给登记位置并区分仍有效/已过期；
**代码事实为真 ≠ 它是本次失败的成因**；CE 里"看起来不一致"的数值先查是不是承重的；
**验收方写的 CE 事实可能是错的，一律自行核实**；
**撞上守卫时改代码，不改守卫、不绕扫描器**；
**复用前轮原语发现不够通用就如实登记前轮缺口**；
**前轮的留痕登记可能正是为你预约的**，动手前 grep 相关注释；
📌 **照搬上一轮的做法前，先确认 CE 在这里是不是也这么做**（W-14 没复制 W-13 的 waypoint 重建，避免了多抽一次 RNG）。
