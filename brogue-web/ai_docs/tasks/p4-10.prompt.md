## 病灶

CE 里"游荡"状态的怪物不是随机乱走，而是**朝最近的 waypoint 走，到了再挑下一个**，所以它们会沿着走廊和房间有目的地巡逻，把地图走遍。web 没有 waypoint 的任何实现（我已 grep 确认 `waypoint` / `wpDistance` 全仓无匹配），WANDERING 怪物的移动缺乏这层结构。

## CE 事实（已逐条核实）

### 一、`setUpWaypoints()` —— Architect.c:3033-3070

```c
// 1) 先把所有"阻挡气味"的格子标成已覆盖
for 每格: if (cellHasTerrainFlag(T_OBSTRUCTS_SCENT)) grid[i][j] = 1;

rogue.wpCount = 0;
rogue.wpRefreshTicker = 0;
fillSequentialList(sCoord, DCOLS*DROWS);
shuffleList(sCoord, DCOLS*DROWS);          // ★ 消耗 RNG

// 2) 按打乱后的顺序扫，挑未覆盖的格子当 waypoint，
//    每挑一个就用 WAYPOINT_SIGHT_RADIUS 的视野把它周围标成已覆盖
for (i = 0; i < DCOLS*DROWS && wpCount < MAX_WAYPOINT_COUNT; i++) {
    x = sCoord[i] / DROWS;  y = sCoord[i] % DROWS;
    if (!grid[x][y]) {
        getFOVMask(grid, x, y, WAYPOINT_SIGHT_RADIUS * FP_FACTOR, T_OBSTRUCTS_SCENT, 0, false);
        grid[x][y] = true;
        rogue.wpCoordinates[wpCount++] = (pos){ x, y };
    }
}

// 3) 给每个 waypoint 算一张距离图
for (i = 0; i < wpCount; i++) refreshWaypoint(i);
```
注意覆盖用的遮挡标志是 **`T_OBSTRUCTS_SCENT`**（与气味图同源），不是视线。`WAYPOINT_SIGHT_RADIUS` 与 `MAX_WAYPOINT_COUNT` 的值请自己查。

### 二、`refreshWaypoint(wpIndex)` —— Architect.c:3014-3031

```c
costMap = allocGrid();
populateGenericCostMap(costMap);
// 沉睡 / 不可移动 / 被囚禁的怪物所在格 → PDS_FORBIDDEN
for 每只怪: if ((SLEEPING || MONST_IMMOBILE || MB_CAPTIVE) && costMap[x][y] >= 0)
                costMap[x][y] = PDS_FORBIDDEN;

fillGrid(rogue.wpDistance[wpIndex], 30000);
rogue.wpDistance[wpIndex][wpCoordinates[wpIndex].x][...y] = 0;
dijkstraScan(rogue.wpDistance[wpIndex], costMap, true);   // ★ 注意第三参是 true
```
**第三个参数是 `true`**，与 safety map 的两次扫描（都是 `false`）不同。请自己读 `dijkstraScan` 确认这个参数的含义再实现，并在报告里说明。

### 三、增量刷新 —— Time.c:2710-2714

```c
rogue.wpRefreshTicker++;
if (rogue.wpRefreshTicker >= rogue.wpCount) rogue.wpRefreshTicker = 0;
refreshWaypoint(rogue.wpRefreshTicker);
```
**每回合只重算一个 waypoint**（建图时才全算）。别每回合全算——那是 O(wpCount) 张 Dijkstra。
这段位于 CE 的**客观时间块**内（web 的 P2-3 已区分主观/客观，**别挂错**）。请自己确认 Time.c:2710 所处的块。

### 四、消费点

- **挑目标 waypoint**：Monsters.c:1200-1230。条件含 `wpDistance[wpIndex][monst.x][monst.y] >= 0` 且 `nextStep(...) != NO_DIRECTION`（即可达），取距离最小者。请完整读这段，别只看我摘的两行。
- **游荡移动**：Monsters.c:3600-3615，`dir = nextStep(rogue.wpDistance[monst->targetWaypointIndex], monst->loc, monst, false);`，到达后换下一个目标。
- Monsters.c:1695-1705 另有一处按 waypoint 距离选点，请一并查看。

### 五、`setUpWaypoints()` 的调用时机

RogueMain.c:707 / 771（关卡初始化），以及 Items.c:5558（地形剧变后，如洪水，重算）。

## ★ 关于 RNG 流与生成基线（任务书曾写错，此处为更正后的版本）

`setUpWaypoints()` 里的 `shuffleList(sCoord, DCOLS*DROWS)` **会消耗 RNG**。但请注意 CE 的调用顺序（RogueMain.c:695-709）：

```c
digDungeon();               // 挖地形
placeStairs(&upStairLocation);
initializeLevel(upStairLocation);   // 内部：populateItems() + populateMonsters()（Architect.c:3790-3791）
setUpWaypoints();           // ★ shuffleList 在这里——所有生成决策都已做完
shuffleTerrainColors(100, false);
```

**也就是说，在 CE 里这次 shuffle 碰不到地形、物品、怪物**——它只移动后续玩法期的随机序列。所以：

- **照 CE 的顺序实现**（地形 → 物品 → 怪物 → waypoint 构建），`generation_baseline.json`（地形指纹 + 怪物数 + 物种 + 物品数）**应当保持绿**。
- 若你实现后发现它**变红了**，说明你把 waypoint 构建插到了生成决策**中途**——那是错的位置，请修正位置，而不是重新捕获基线。
- `p2_3_baseline.json` 的 **play 段仍会变红**（游荡怪行为改变 + 玩法期 RNG 流移动），这是预期内的，**如实报告、不许刷新**，由验收方裁决。

另注 RogueMain.c:771：重访已生成过的关卡时也会再调一次 `setUpWaypoints()`（地图是从存储恢复的，不重新生成）。web 若有对应的重访路径，一并处理；没有就登记。

## 测试要求

1. 每条断言必须能在某个具体的错误实现下失败。禁止"调用了就算过"。
2. **对抗性测试至少五条**，报告写明各自捕获哪种错误实现。必须覆盖：
   - **覆盖性**：waypoint 集合应覆盖全图可通行区域（挑一批随机地板格，断言每格都在某个 waypoint 的 `WAYPOINT_SIGHT_RADIUS` 覆盖内，或至少存在可达 waypoint）

   - **游荡怪确实在走向 waypoint**：放一只 WANDERING 怪，跑若干回合，断言它到 `targetWaypointIndex` 的 `wpDistance` 单调下降（而不是原地打转或随机游走）
   - **到达后换点**：抵达后 `targetWaypointIndex` 必须改变
   - **沉睡/不可移动/被囚禁的怪物格被标为不可通行**（`refreshWaypoint` 那段）
3. **反向验证（强制）**：至少两条断言**真的改坏**、跑出真实失败输出、粘进报告、再还原。
4. **决定性**：同种子必须得到同一套 waypoint，要有测试锁住。
5. **对照组**：非 WANDERING 状态的怪物行为完全不变。
