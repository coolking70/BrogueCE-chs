## 三个函数（请完整读原文，下面只是路标）

### 一、`removeDiagonalOpenings()` —— Architect.c:1913-1950

消除"对角穿缝"：两个阻挡通行且阻挡对角移动的格子呈对角排列、另两个对角是通路时，
随机挑一侧把墙推开，使玩家不能从对角缝里钻过去。

要点：
- 外层是 `do { ... } while (diagonalCornerRemoved)`——**反复扫到没有为止**，不是扫一遍。
- 内层 `for (k = 0; k <= 1; k++)` 同时试两种对角朝向。
- `rand_percent(50)` 决定推开哪一侧。
- 判据里同时用了 `T_OBSTRUCTS_PASSABILITY` 与 `T_OBSTRUCTS_DIAGONAL_MOVEMENT`
  两个旗标——**web 有没有"阻挡对角移动"这个概念？没有的话怎么近似？**
  请查清后在报告里说明取舍。

### 二、`finishDoors()` —— Architect.c:2733-2758

```c
const short secretDoorChance = clamp((rogue.depthLevel - 1) * 67 / (gameConst->amuletLevel - 1), 0, 67);
for 每个非机器的 DOOR 格:
    if ((左或右可通行) && (上或下可通行)) {
        → FLOOR;                      // 孤儿门：四面都通，门没有意义
    } else if (四正方向里阻挡通行的邻格 >= 3) {
        → FLOOR;                      // 孤儿门：几乎被封死
    } else if (rand_percent(secretDoorChance)) {
        → SECRET_DOOR;                // ★ 随深度升高的密门概率，最高 67%
    }
```

**注意 `machineNumber == 0` 这个条件**——机器内部的门不参与，否则会破坏宝库。
web 的机器标记方式见 `BlueprintEngine.ts`（P1-33 用的是 `CHARRED_FLOOR` 权宜做法，
见路线图 P1-37）——请判断该用什么作为"属于机器"的判据，并说明。

**`amuletLevel` 的实际数值请自己查 `gameConst`**，不要照抄转述。

### 三、`finishWalls(boolean includingDiagonals)` —— Architect.c:2480-2517

把裸露的花岗岩补成墙、把未裸露的墙退回花岗岩。请完整读。

## ★ 本轮的两个风险点

1. **密门会影响连通性判据**。`Game.canMoveTo` 排除 `SECRET_DOOR`
   （见 SESSION_HANDOFF 的"已知代码坑"）。深层最高 67% 的门变密门后，
   **P1-33 建立的"坏层为 0"可能被击穿**——但那是**假阳性**：CE 里密门是可以
   被发现并打开的，不是真墙。
   请先查明 web 有没有"搜索/发现密门"的机制：
   - 有 → 连通性判据应当把密门视作可通行（与 CE 的 `T_PATHING_BLOCKER` 口径对齐，
     请核实 CE 的密门是否带该旗标）；
   - 无 → **本轮不要让密门数量失控**，并把这个缺口显式登记。
   **无论哪种，都不许通过"少生成密门"来绕过。**

2. **孤儿门移除会改变门的总数**，进而影响 C-0 的环路统计
   （`c_0_add_loops.test.ts` 有"新开门数 > 15"之类的断言）。若变红，
   **先判断是不是孤儿门被正确移除**，再决定是调整断言还是修实现——
   **不许直接放宽**。参考 C-1 那轮的阈值校准要求：必须论证新阈值仍有牙。

## 一个已知会咬人的陷阱（C-2 实证，务必先读）

地形枚举的深水成员叫 **`WATER_DEEP`**，不是 `DEEP_WATER`。C-2 那轮在生产代码
和测试里先后误写成后者，**`npm test` 并不会报错**——vitest 走 esbuild，只剥类型
不做类型检查，写错的枚举成员运行时得到 `undefined`，表现为一连串莫名其妙的行为
失败而非编译错。只有 `npm run build` 里的 `vue-tsc` 才会报 `TS2339`。
**所以：任何一次让你困惑的测试失败，先跑一遍 `npm run build`。**
