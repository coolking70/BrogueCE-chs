# V-2b-4 祭坛族轮：拆掉自创祭坛组 + 8 地形 3 DF + CE 逐字落七条蓝图

## 0. 先读：本轮有一条用户裁决

web 有一套**自创的祭坛组玩法**：从某个祭坛取走物品 → 同组其余祭坛塌成 `CHARRED_FLOOR`
并销毁其上物品（`Game.ts:3189-3212`）。**CE 完全没有这个机制。**

**用户已拍板：让 CE 祭坛接管，拆除自创玩法。** 依据是项目的既定裁决一「全量对齐、
不留宽松度」——自创玩法属偏离，不是设计。

验收方已把这套子系统的边界量清楚（下面数字你可以复核，但不必重新发现）：

| 组成 | 位置 | 性质 |
|---|---|---|
| 取物塌陷 | `Game.ts:3189-3212` | 自创玩法本体 |
| `MF_ALTAR_GROUP` 旗标 | `blueprints.json` 数据 + `BlueprintEngine.ts:1152-1156` 消费 | **CE 无此旗标**（`Rogue.h` 零命中） |
| `altarGroupId` 字段 | `BlueprintEngine.ts:117/308/958/1330`、`Grid` 的 Cell | **CE 无 altar group 概念**（全库零命中） |
| `Architect.altars` 数组 | `Architect.ts:191/390` | **只 push、无人读**——死数组（`Architect.ts:194` 的注释自己已承认） |

⚠️ **拆除时的唯一陷阱**：`BlueprintEngine.ts:1153` 的
`altarGroupId = this.depth * 100 + rng.randRange(1, 99)` **会掷骰**。删掉它就少掷一次，
生成流随之移动——这是本轮**有意**的变更（基线本来就要重捕获），但你必须在报告里
**把它单列为一条基线偏离成因**，不要让它混进"新蓝图入池"那一堆里说不清。

`Architect.machines` 数组同样无消费者（同一条注释里提到）。**它不在本轮范围**——
它服务的是钥匙/锁逻辑，归钥匙轮；本轮只拆 `altars`。若你发现 `machines` 实际有读者，
指出来。

## 2. 七条蓝图（CE 目录序，逐字）

1 Mixed item library · 2 Single category library · 6 Commutation altars ·
7 Resurrection altar · 15 Statuary（护符房）· 26 Nested item library ·
28 Throwing tutorial（笼子收回版）

⚠️ **15 号触及护符来源双轨**（V-2b-0 §4 风险 5）：web 现在在 D26 由
`Game.populateLevel:1204-1216` **直投**护符；CE 的护符房是机器。两套来源叠加会发出
**两个**护符。**本轮必答**：落 15 号时一并处置，倾向"机器接管、直投退位"，
但要先实测确认 15 号在 D26 的建成率——若它并非必然建成，直投退位会导致某些局
**拿不到护符**（那是致命的）。把实测数据写进报告再下结论。

## 3. 基线重捕获（最后一步）

本轮移动生成流的成因至少三股，报告里要**分开**：
① 拆掉 `altarGroupId` 的掷骰（少一次 `randRange`）；
② 七条新蓝图入池（改变抽签）；
③ 新地形/DF 落地。

V-2b-3 用受控单变量实验把两股成因干净分开了（结论"234 = 100% 新蓝图、通电机制 0"），
本轮沿用同样做法。**分不开就说分不开**，不要编。
