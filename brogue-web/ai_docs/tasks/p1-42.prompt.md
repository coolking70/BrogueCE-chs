## 一、病灶

C-3 让密门按 CE 概率如实生成（D26 封顶 67%，实测 5 种子 × D1-D26 共 327 扇）。
与此同时，`p1_26` / `p1_29` / `p1_33` 三个连通性闸门的判据已按 CE 口径
（`Architect.c:202-203`：`T_PATHING_BLOCKER && !TM_IS_SECRET`）改为**放行密门**
——见 `src/test/harness.ts` 的 `analysisAllowsMove`。

**那个口径在生成器层面是对的，但它的前提是"玩家找得到密门"。**
而 web 的发现机制远弱于 CE：

- **web**（`Game.ts:6390-6404`）：玩家移动后，对**四正邻接**的 SECRET_DOOR
  以固定 30% 揭示。没有半径、没有斜向、没有主动命令、没有充能、没有感知加成。
- **CE**：`search(searchStrength)`（`Movement.c` 附近 2459，自己确认）
  是**半径 = strength/10 的方形区域**扫描，命中率 = `strength − 距离×10`，
  对带 `T_OBSTRUCTS_PASSABILITY` 的格再乘 2/3，且要求 `playerCanDirectlySee`；
  `percent >= 100` 时还顺带标记 `KNOWN_TO_BE_TRAP_FREE`。
  两个调用源（自己确认）：
  1. **每走一步的低强度自动搜索**（`Time.c` 附近 2544-2549）：
     `search(rogue.awarenessBonus + 30)`，且**每格只触发一次**
     （`SEARCHED_FROM_HERE` 旗标，`Rogue.h:1090`）；
  2. **主动 search 命令**（`Time.c` 附近 2395-2423）：连续回合"充能"，
     `STATUS_SEARCHING` 累加，满 5 时做一次强力搜索；非连续回合会清零。

**后果**：一扇离走廊两格的密门，CE 的玩家搜得到，web 的玩家可能永远撞不开。
若唯一通路在它之后，那一层实际不可玩——而闸门会报绿。

## 二、要做什么

### 1. 移植 `search(searchStrength)`

照 CE 实现：半径、距离衰减、阻挡格的 2/3 折扣、可见性要求。
**`playerCanDirectlySee` 在 web 的对应物是什么，请自己查明**
（`Game.hasLineOfSight` 或 FOV 的 `isVisible`——两者语义不同，选哪个要在报告里论证）。

`KNOWN_TO_BE_TRAP_FREE`：web 有没有对应设施？**有就接上，没有就登记不实现。**

### 2. 接上两个调用源

- **每步自动搜索** + `SEARCHED_FROM_HERE` 的"每格只一次"语义
  （需要 `Cell` 新增一个布尔位；`Grid.ts` 已在允许清单）。
  `rogue.awarenessBonus` 在 web 的对应物：**感知戒指（awareness）**。
  查明 web 有没有把它接进任何地方；没有就用 CE 的基线值并登记。
- **主动 search 命令**：web 的按键处理在 `src/engine/Input.ts`。
  接上 `s` 键 + 充能语义。**若与既有按键冲突，停下来报告，不要擅自改键位。**

### 3. 替换旧的 30% 邻接揭示

它是 web 自创的近似，被上面两条取代。**不要保留两套**——
留着就又是一个"同一件事多套答案"（P1-38 的教训）。

## 三、★ 必须实测并报出的（本轮的核心判据）

1. **修复前后对比**：同样 15 种子 × D1-D26，
   随机行走 N 回合后，密门被发现的**比例**各是多少。
2. **最坏情形**：是否存在"唯一通路在密门之后"的层？有多少？
   修复前后玩家在 N 回合内找到它的概率各是多少。
   （这条正是 P1-42 存在的理由——**请认真量**。）
3. 主动搜索充能满 5 次时的实际发现率。
4. 决定性：同种子同操作序列，发现结果一致。
