# V-2b-3 wired 触发网络：把机器"通电"接起来

## 0. 先读这段：勘察报告把本轮的起点说低了

勘察报告 §0 称 M1 wired 网络「web 为零」、M3 DF 系统「web 完全没有」。**验收方实测，两条都过头了**：

| 勘察报告说 | 实际 |
|---|---|
| wired 网络 web 为零 | **`promoteTile` 已完整实现**（`Promotion.ts:219`，C-4c 轮，含 `TM_VANISHES_UPON_PROMOTION`、`fireType`/`promoteType` 分派、每回合两趟驱动）。三个触发源也在：`promoteOnStep` / `promoteOnItemPickup` / `promoteOnItemPlaced`（`:349/:354/:359`） |
| DF 系统 web 完全没有 | **`spawnDungeonFeature` 在**（`DungeonFeature.ts:673`），DF 目录 **28 条**、闭包完整无悬空引用（测试钉死），DFF_* 旗标齐全 |

勘察报告真正成立的那半是：**蓝图 `FeatureDef` 没有 df 列**（验收方复核属实），以及 DF 目录远小于 CE。那两件归 V-2b-7，不是本轮。

**所以本轮的起点是：`promoteTile` 只差 wired 那一个分支。** `Promotion.ts:316` 处：

```ts
if (!useFireDF && (tile.mechFlags & TM_IS_WIRED)) {
```

分支体目前只置一个 `wiredBranchHit: true` 的留痕，什么都不做（文件头注第 5 条写明「C-4d 未实现留痕——本轮不做任何事」）。

**这是一处登记占位，本轮要做的是「留痕反转」**：占位的前提（wired 未实现）本轮变为假，按项目惯例**不是删掉断言，而是把断言反过来主张新事实**——原先钉「命中 wired 分支时什么都不发生」的测试，要改成钉「命中时真的通电了」。找出所有钉 `wiredBranchHit` 的测试并逐个反转，不要只改实现。

## 1. 要实现的四件（CE `Time.c`）

### 1.1 `activateMachine(machineNumber)` — `Time.c:1173-1199`

对全图扫描，命中条件四个全满足才处理：`IS_IN_MACHINE` ∧ `machineNumber` 相等 ∧ **未** `IS_POWERED` ∧ 该格有 `TM_IS_WIRED`。命中则置 `IS_POWERED`，再对每个带 `TM_IS_WIRED` 的层调 `promoteTile(x, y, layer, false)`。

**⚠️ 这个函数消耗 RNG**：CE 先 `fillSequentialList` + `shuffleList` 洗了行序与列序各一次（`:1177-1180`），然后按洗过的序扫。**必须照做**——省掉洗牌会让 RNG 流分叉，且落位顺序与 CE 不同。

### 1.2 `IS_POWERED` 格标记

新增单元格标记。注意它的生命周期很短：见 1.3 的"电随即散去"。

### 1.3 `promoteTile` 的 wired 分支 — `Time.c:1273-1287`

```
if (!useFireDF && (tile->mechFlags & TM_IS_WIRED)
    && !(pmap[x][y].flags & IS_POWERED)
    && !circuitBreakersPreventActivation(pmap[x][y].machineNumber)) {
    pmap[x][y].flags |= IS_POWERED;
    activateMachine(pmap[x][y].machineNumber);
    // 电在结束后立即从全图散去
    for (i…) for (j…) pmap[i][j].flags &= ~IS_POWERED;
}
```

三个要点，缺一个就出错：

1. **与 `activateMachine` 是相互递归**（它调 promoteTile，promoteTile 又可能调它）。`IS_POWERED` 就是防无限递归的那道闸——先置位再递归。
2. **CE 注释明说「机器不必连续」**（`:1277-1278`）——所以是按 `machineNumber` 全图扫，不是按连通区域扩散。
3. **结束后把全图的 `IS_POWERED` 清掉**，不是只清本机器的。这是最容易漏的一步。

### 1.4 `circuitBreakersPreventActivation` — `Time.c:1230-1242`

本机器内任意一格带 `TM_IS_CIRCUIT_BREAKER` → 返回 true，阻断激活。

### 1.5 顺带补一个 failsafe（V-2b-2b 验收登记）

`BlueprintEngine.ts:1193` 的 `MF_REPEAT_UNTIL_NO_PROGRESS` do-while
（`} while (repeatUntilNoProgress && roundPlaced >= minInstances);`）**没有迭代上界**。

V-2b-2b 把 `personalSpace=0` 对齐 CE 改成「不占格」之后，
「REPEAT + reqSpace 0」的组合在理论上永不终止：不占格 → 下一轮候选不缩减 →
每轮都落满 → 条件恒真。

**验收方已核**：CE 全部 10 条带 `MF_REPEAT_UNTIL_NO_PROGRESS` 的 feature，
`reqSpace` 逐条都是 1，所以当前无数据载体；CE 自身结构也一样，不是 web 特有缺陷。
**但**蓝图表还要从 27 条长到 71 条，届时一个 `reqSpace` 打错就会让生成
**静默挂死、没有任何诊断**——这种故障在门禁里表现为 worker 超时或 OOM，
极难定位（V-2b-2b 已经因为别的原因吃过三次 worker OOM）。

**本轮加一个 failsafe**：给该 do-while 一个迭代上界，超限时**显式抛错**并在
消息里带上蓝图 id、feature 序号与轮数。上界取一个明显不可能达到的值
（参考 CE 的 failsafe 惯用量级，例如 1000）。

这是**纯防御**：可达路径上零行为变化，不掷骰、不改落位、不动基线。
若你认为 CE 有等价的显式上界而 web 该照抄那个值，**行使授权反驳**并给出行号。
