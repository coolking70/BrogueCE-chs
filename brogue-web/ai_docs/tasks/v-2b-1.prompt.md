## 0. 本轮的定位

V-2b-0 勘察查明：蓝图全表扩充（web 20 → CE 71）真正卡在四套缺失的引擎机制上，不是地形符号。九轮拆法里，本轮是**第一轮，也是唯一一轮不解锁新机制的**——它把「落位语义」和「历史垃圾」清干净，让后面八轮的 CE 数据能按 CE 口径落。

**为什么必须先做**：CE 的 71 条数据全部按 CE 的 personalSpace / NEAR_ORIGIN 口径设计。地基不正，每条数据都得按错误口径折算一遍，之后还要整体返工。反正扩表必然重捕获基线，修一次引擎省 71 条折算。

本轮会移动生成流，基线必须重捕获（§3，**最后一步**）。

## 1. 六件事

### 1.1 personalSpace 口径对齐 CE

验收方已逐行比对，差异**只有一处**，不要修多了：

| | 循环范围 | 边长 | ps=2 时清几格 |
|---|---|---|---|
| CE（`Architect.c:1462-1470`） | `featX-ps+1 .. featX+ps-1` | **2ps−1** | 3×3 = 9 |
| web（`BlueprintEngine.ts:1074-1079`） | `-r .. r` | **2r+1** | 5×5−1 = 24 |

CE 自己的注释写得很明白（`Architect.c:1459-1460`）：「0 means nothing gets cleared, 1 means only the tile itself, and 2 means the 3x3 grid centered on it」。

**中心格的差异是假象，不要动**：web 的 `markPersonalSpace` 里 `if (dx===0 && dy===0) continue` 看似漏了中心格，但中心格在 `BlueprintEngine.ts:778` 已由 `usedCells.add(pos)` 单独加入；CE 则是在同一个循环里把中心格一并置 `occupied`。**两边等价**，改了反而错。

所以本项只改边长：`2r+1` → `2r-1`（即循环范围 `-(r-1) .. (r-1)`）。注意 `ps=0` 时 CE 不清任何格，新公式下 `-(-1)..(-1)` 自然为空，行为正确；`ps=1` 只清中心格（已由 778 行覆盖）。

### 1.2 `MF_NEAR_ORIGIN` 的距离基准 center → origin

`findFeaturePosition(available, used, center, origin, feature, fFlags)`（`BlueprintEngine.ts:1030` 一带）里，`MF_NEAR_ORIGIN` 分支用 `center.x/center.y` 算曼哈顿距离（约 1055 行）。

CE 的 ORIGIN 系旗标**全部**以 `originX/originY` 为基准：
- `MF_NEAR_ORIGIN` / `MF_FAR_FROM_ORIGIN` 的 `distance25` / `distance75` 界（`Architect.c:1336-1341`）取自以 origin 为源的距离图；
- `MF_IN_VIEW_OF_ORIGIN` / `MF_IN_PASSABLE_VIEW_OF_ORIGIN` 直接 `getFOVMask(p->viewMap, originX, originY, …)`（`Architect.c:1343-1349`）。

改成用第 4 个参数 `origin`。**对全部 BP_ROOM 机器都是行为变化**（前厅机器 center==origin，不受影响）。

### 1.3 死代码清除

验收方实测确认（勘察报告说「两数组」，实为两数组 + 两死循环，逐一列出）：

| 位置 | 现状 |

| `Architect.ts:193` `public cages` | 声明，**从未 push** |

| `Game.ts:1260` `for (const cage of cages)` | 死循环 |
| `Game.ts:1082` / `:1128-1129` | 两数组的传参与形参 |

全部删除，连带形参。

**删除前必须先补一条断言**（这是硬要求，不是可选项）：V-2a 给前厅机器豁免了 `blueprint_center` 的「center 可通行」检查，豁免的安全性**正建立在这条死代码上**——因为没有任何活代码把宝藏放在 center。删掉死代码后这个前提就靠不住了（将来谁重新接线都会踩坑）。所以要在 `blueprint_center.test.ts` 里补一条显式断言：**没有任何生产代码把物品投放到机器 center**（形态自定，性质断言或扫描皆可），把安全前提从「碰巧没人用」搬成「有测试钉住」。

### 1.4 三个 web 自创旗标清除

勘察报告说「现存 9 处、8 条蓝图」，**验收方实测是 16 处**，逐条列出：

- `MF_SCATTER` × 14（`blueprints.json` 行 402/475/486/517/527/558/568/598/711/721/731/760/770/780）
- `MF_RING` × 1（行 639）
- `MF_FILL_DOORWAY` × 1（行 341）

**关键事实：引擎一处都不消费。** `findFeaturePosition` 只认 `MF_BUILD_AT_ORIGIN` 与 `MF_NEAR_ORIGIN` 两个放置旗标（约 1045/1049 行），这三个是惰性数据。

所以直接删除即可，**不需要「替换成 CE 等价物」**——它们本来就没在起作用，硬塞一个 CE 旗标反而是引入新行为。若你读代码发现某处确实被消费（验收方可能看漏），**行使授权反驳**并给出行号。

### 1.5 `minimumInstanceCount` 全表显式化

`BlueprintEngine.ts:33-41` 的注释挂了这笔账：V-2a 起新增 feature 按 CE 原值显式给出，既有 feature 仍缺省取 `instanceCount[0]`。本轮全表显式化，按各自 CE 对应物的 `minInsts` 原值填。

web 自创的、CE 无对应物的 feature，沿用 `instanceCount[0]` 并显式写出（保持行为不变，只是把隐式变显式）。

### 2.2 风险 1（勘察报告 §4）在本轮就会撞上

web 的 `ALTAR` 带一个**自创语义**：从祭坛取物 → 同 `altarGroupId` 的其余祭坛塌成 `CHARRED_FLOOR` 并销毁其上物品（`Game.ts:3232-3245`）。CE 的祭坛没有这个行为。

27 号 Secret room 用 `ALTAR` 作 `ALTAR_INERT` 的替身，其上放的是 `MF_ADOPT_ITEM` 领养来的物品。若该祭坛被分配了 `altarGroupId`，玩家取走物品就会触发自创塌陷。

**本轮必答**：确认 27 号落下来的祭坛是否会进 altarGroup（读 `Architect.ts:381-392` 的入组条件）。
- 若不会进组 → 写明理由，本项无风险，登记给 V-2b-4。
- 若会进组 → 本轮就要处置：**倾向于让 27 号的祭坛不进组**（最小改动、不触碰既有 web 祭坛玩法）。若你认为该直接拆除自创塌陷语义，**先在报告里申请**，不要自行拆——那会动到现存玩法，超出本轮范围。

## 7. 门禁与报告

```
npx vitest run
npm run build
```

- `npx vitest run` 是**并行**的。不要加 `--fileParallelism=false`：串行复用单 worker，反而制造跨文件的模块单例污染。
- 类型门禁用 `npm run build`（vue-tsc -b 套用 `tsconfig.app.json` 的 `noUnusedLocals`），**不要**用 `npx tsc --noEmit`，它漏未使用变量。本轮删死代码，未使用变量的风险高，这条尤其要紧。

- 全量门禁墙钟约 23 分钟（V-2a 校准后实测），属正常，不要因为慢就中断。
