# 第一件：P1-37 宝库地板用地形类型冒充标志位

## 病灶（这是验收方的边界设计逼出来的，不是上一轮的错）

P1-33 修机器割点时，需要让**楼梯不落在宝库内部**（否则封住宝库门就把上楼梯
关了进去）。CE 的做法是**旗标**：楼梯/物品/怪群落点一律回避 `IS_IN_MACHINE`
（Architect.c:3543 / 3597 / 3712 / 3738）。

web 的 `populateLevel` 从 `terrain === FLOOR` 的牌堆抽楼梯，而 `Game.ts` 在
P1-33 的文件边界内被禁改，于是开发方把**宝库地板改判为 `CHARRED_FLOOR`**
让它退出牌堆。目的达到了（坏层 5→0），但这是**用地形类型冒充标志位**。

## 已确认的副作用（验收方实测）

规模：15 种子 × D1-D26 = 390 层里 **21745 格**被改判（约每层 56 格）。

1. **玩家可见**：`Game.ts` 的地形描述把 `CHARRED_FLOOR` 说成**"烧焦的地面"**，
   颜色 `0x554433`。玩家走进宝库看到一片焦土——CE 的宝库地板是正常地面。
2. **卷进火焰系统**：`Gas.ts:128` 的"焦土偶尔长草"机制会作用在宝库地板上，
   且**每格每回合消耗 RNG**（`randPercent(1) && randPercent(5)`）。
   既是行为偏差，也是无谓的随机流消耗。

## 必做

1. 引入 `IS_IN_MACHINE` 等价旗标（cell 上的布尔位，或独立的机器掩码图——
   **你选，并说明理由**；注意它要能穿过存档往返，或明确登记不穿）。
2. 让**楼梯落点**回避它（对应 CE Architect.c:3543 的语义；
   物品与怪群的回避若 web 有对应路径也一并接上，没有就登记）。
3. **把宝库地板恢复为普通 `FLOOR`**，并确认"烧焦的地面"描述与长草机制不再作用于宝库。
4. **硬闸门：坏层必须仍为 0**。`p1_33_machine_chokepoint.test.ts` 与
   `p1_26_invariants.test.ts` 的断言必须继续通过。若变红，说明旗标没接对，
   **停下来报告，不要回退成 CHARRED_FLOOR 了事**。

## 必须实测汇报

- 修复前后 `CHARRED_FLOOR` 的格数对比（预期从每层 ~56 格降到"只有真的被烧过的格"）。
- 坏层数（至少 15 种子 × D1-D26）。

## 一个已知会咬人的陷阱（C-2 实证，务必先读）

地形枚举的深水成员叫 **`WATER_DEEP`**，不是 `DEEP_WATER`。C-2 那轮在生产代码
和测试里先后误写成后者，**`npm test` 并不会报错**——vitest 走 esbuild，只剥类型
不做类型检查，写错的枚举成员运行时得到 `undefined`，表现为一连串莫名其妙的行为
失败而非编译错。只有 `npm run build` 里的 `vue-tsc` 才会报 `TS2339`。
**所以：任何一次让你困惑的测试失败，先跑一遍 `npm run build`。**
