# 任务 P1-26：把相位快照基线换成不变量断言

工作目录已是 `brogue-web/`。C 原版在 `../BrogueCE-master/src/brogue/`（唯一事实来源，**只读**）。

**授权反驳条款有效**：本任务书的事实陈述可能有错，CE 源码优先。

**背景**：本轮已由项目负责人拍板，是 Phase C（生成器重写）的**前置条件**。设计依据见 `ai_docs/phase_c_generator_proposal.md` §6.2，路线图条目见 `dev_roadmap_2026Q3.md` 的 P1-26。

## 病灶

`src/test/p2_3_objective_time.test.ts` 的 F 段有一条活的断言：

> 「4 seed × 400 回合玩法状态与 p2_3_baseline 一致」

它逐字比对 400 回合后**玩家坐标、HP、深度、每只怪物的名字@坐标:血量**。问题是：**任何有意的行为改动都会让它变红**。

已经发生过的：P4-8（气味追踪 + stealthRange 对齐 + 3% 掷骰）把它打红，只能由验收方授权重捕获。即将发生的：P4-9（safety map 改变逃跑路径）、P4-10（waypoint 改变游荡路径）必然再撞；进入 Phase C 后每一步都会红。

这与先前 `p2_baseline` / `p2_2_baseline` / 本文件 F 段的 levels 部分被退役为 `it.skip` 是**同一个毛病：相位快照当回归闸门用**。它抓不出真回归（因为每次都"预期会变"），只制造噪音和"顺手刷新基线"的压力——而这种压力正是最危险的，它会训练所有人把红灯当背景音。

## 必做

### 一、退役 play 段的逐字比对

把那条断言改为 `it.skip`，或删除后由下面的不变量接管——**你选，但要在报告里说明理由**。若保留为 skip，注释里必须写清"为何退役"，与同文件 levels 段的处理保持一致。

### 二、新建不变量断言（本轮的主体）

新增测试文件，对 **5 个种子 × D1–D26** 做**不依赖具体坐标**的断言：

1. **上下楼梯存在**：每层（D26 除外，它不生成下楼梯——请自行确认这是否属实，别照抄我的说法）都有上楼梯与下楼梯。
2. **上楼梯能走到下楼梯** —— **本轮最重要的一条，见下方第三节**。
3. **地板占比在合理区间**：统计可走格数，断言落在一个宽区间内（区间由你实测后定，要留足余量，目的是抓"生成器彻底失灵"而不是抓正常波动）。
4. **D1–D26 全部生成不抛异常**。
5. **决定性**：同一种子跑两次，地形指纹一致。

**判据必须用实际移动规则**：`Game.canMoveTo` 排除 `GRANITE`/`WALL`/`SECRET_DOOR`/`LOCKED_DOOR` **和 `WATER_DEEP`**，但**不排除 `LAVA`**（见路线图 P1-25）。请自己读 `Game.ts` 的 `canMoveTo` 确认当前口径，**不要用 `cell.isPassable`**——深水的 `isPassable` 是 `true`，用它量连通性会让 bug 完全隐形（验收方就这么错过一次，详见 phase_c 文档 §四的自我纠错记录）。

### 三、★ 第 2 条不变量现在会失败，这是预期的

验收方实测（5 种子 × D1–D26 = 130 层，从上楼梯按 `canMoveTo` 泛洪）：

```
16/130 层的下楼梯从上楼梯走不到
其中 5 层是 D26（本身无下楼梯）→ 真正坏掉 11/130 ≈ 8.5%
最坏：seed 20260913 D1 从上楼梯只能走到 1 格（345 格孤岛）
      seed 20260916 D14 只够到 20/350
```

根因是 web 缺了 CE 的湖泊连通性验证（Architect.c:2588-2688：每提议一个湖就 flood-fill 验证放下后是否仍连通，不通过换位重试 9 次、仍不行则放弃该湖改生成更小的）。**修复不在本轮范围**，下一轮（P1-29）做。

所以本轮请按项目一贯的**显式留痕**做法（参考 P4-3 的 `MONST_GETS_TURN_ON_ACTIVATION`、P4-6 的玩家侧留痕、P1-28 续轮的"闸门/内容"拆分）：

- 第 2 条不变量写成**记录现状的断言**：断言"下楼梯不可达的层数 **恰好等于** 当前实测值"，并在测试描述里写明：**这是已知 bug（P1-29 待修），修复后本断言应改为严格 0**。
- 用"恰好等于"而不是"不超过"——这样**变好和变坏都会翻红**，修复落地时会强制有人回来改这条，不会被悄悄忽略。
- 实测值以**你自己跑出来的为准**，不要照抄我上面的数字（我用的种子集合未必与你选的一致）。请在报告里贴出你的实测明细。

1. 每条不变量必须能在某个具体的生成器故障下失败。禁止"跑通了就算过"。
2. **反向验证（强制）**：至少两条，**真的把判据改坏**（例如把 `canMoveTo` 口径换成 `isPassable`、把楼梯存在性判定注释掉），跑出真实失败输出，粘进报告，再还原。
   - 其中**必须有一条**验证"用 `isPassable` 量连通性会让 8.5% 的 bug 隐形"——这正是验收方踩过的坑，值得用测试钉死。
3. 新不变量的执行时间要可接受（5 种子 × 26 层 × 泛洪）。若超过 60 秒，减少种子数并在报告说明。
