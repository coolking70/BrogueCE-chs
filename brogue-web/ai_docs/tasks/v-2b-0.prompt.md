# V-2b-0 勘察轮：蓝图全表扩充到底被什么卡住

## 0. 为什么先勘察，不直接扩表

原计划的 V-2b 是「`blueprints.json` 按 CE 全表重写，web 20 条 → CE 71 条」。验收方做了一次粗测，结论是**这一轮按原样投不下去**：CE 蓝图引用的地形/怪物/地牢档案，web 大面积没有载体。照抄会造出死数据 —— 这正是 V-2a 报告 §1.3 已经实证过的事（`vestibule_flammable` 等三个前厅无法按 CE 落地，因为缺 `WOODEN_BARRICADE`、`SCROLL_SHATTERING`、`TRAP_DOOR_HIDDEN` 等载体）。

**本轮不实现任何东西，只产出一张能拿去拆轮次的账。**

## 1. 验收方的粗测（**近似值，本轮的任务之一就是纠正它**）

用脚本把 `GlobalsBrogue.c:174-621` 的 71 条蓝图逐条抽符号，与 web `Grid.ts` 的 `TerrainType`（47 个成员）+ `monsters.json`（67 条）对差：

- CE 蓝图 **71** 条；web **20** 条（reward 5 / key_guard 7 / vestibule 4 / thematic 4）
- 粗测「无需新载体即可落地」**仅 6 条**：Outsourced item、Plain secret door、Idyll、Swamp、Camp、Dismal
- 缺口符号 **88** 个，按解锁蓝图数排序的前几名：

| 解锁条数 | 符号 | 类别 |
|---|---|---|
| 14 | `ALTAR_SWITCH` | 地形 |
| 13 | `STATUE_INERT` | 地形 |
| 10 | `ALTAR_INERT` | 地形 |
| 9 | `CARPET` | 地形 |
| 7 | `MACHINE_GLYPH` | 地形 |
| 5 | `MK_GUARDIAN` | 怪物 |
| 5 | `MACHINE_TRIGGER_FLOOR` | 地形 |
| 4 | `PEDESTAL` / `TORCH_WALL` / `WALL_LEVER_HIDDEN` | 地形 |

**已知这份粗测有系统性误差，不要照单全收**：web 有通用的 `ALTAR` / `SACRED_GLYPH` / `PRESSURE_PLATE` / `TRAP`，所以 `MACHINE_GLYPH`、`MACHINE_PRESSURE_PLATE` 之类很可能**只是命名不同**而非真缺口；反过来 CE 的八种祭坛变体 web 只有一个通用 `ALTAR`，那是真缺口。**分清这两者正是本轮的核心工作**，脚本分不出来，得人读两边代码。

## 2. 本轮要产出的三样东西

### 2.1 权威载体映射表

对 88 个缺口符号逐个判定，落到四类之一：

| 判定 | 含义 |
|---|---|
| **已有（别名）** | web 已有等价载体，只是名字不同 —— 写出 web 侧的名字 |
| **已有（退化）** | web 有通用版但 CE 分了变体 —— 写清 CE 分了几种、差异是什么（行为差异，不只是外观） |
| **真缺口** | web 完全没有 —— 估一下实现难度（纯地形条目 / 需要新机制 / 需要新怪物 AI） |
| **不适用** | 解析噪音（如 `BLUEPRINTS`、`FEATURES` 这类注释里的词）|

每条都要给 CE 的 `文件:行号`。

### 2.2 逐蓝图的可落地判定

71 条逐条标注：**现在就能落地 / 缺 N 个载体（列出）/ 依赖新机制（说明哪个）**。
按 CE 的五节组织（REWARD ROOMS / AMULET HOLDER / VESTIBULES / KEY HOLDERS / FLAVOR MACHINES）。

### 2.3 拆轮建议

按依赖顺序给出拆法，每轮说明：范围、前置、能解锁多少条蓝图、为什么这几件必须同轮（耦合理由）。

拆的原则参考 V-1c 的先例：**相互耦合的不能拆**（资格过滤 / 配额 / 递归 / 回滚四件当初就必须同轮，拆了任何一件另外三件都不成立）。反过来，**能独立验证的就该拆开**。

如果你的结论是「某一轮不可避免地很大」，说清楚为什么不能再拆 —— 这个判断验收方会认，只要理由成立。

## 3. 必读的前情

- **V-2a 报告 `ai_docs/v_2a_report.md` 的 §9**（六条遗留），尤其第 1 条：CE 的 16 条 `BP_ADOPT_ITEM` 蓝图**全部**带 `MF_ADOPT_ITEM` 消费 feature，web 7 条 key_guard **一条都没有** —— 也就是「守卫机器持有钥匙」在 web 其实没真正成立（KEY 指令被领养机制读走后丢弃，钥匙仍由锁驱动近似）。这可能本身就该是独立一轮。
- V-2a 报告 §9.5 的 **`personalSpace` 语义偏差**：web `markPersonalSpace` 清 (2r+1)²-1 格、CE `personalSpace=2` 清 3×3，差一位。统一修法会移动全部机器布局（动则重捕获基线），当初登记给 V-2b 评估 —— 本轮要给出「该不该修、放哪一轮」的建议。
- **蓝图旗标审计表**（路线图里，V-1b 产出）：三个 web 自创旗标 `MF_SCATTER` / `MF_RING` / `MF_FILL_DOORWAY` 要整体替换，本轮要说明替换成 CE 的什么、影响哪些现存蓝图。
- **两处 V-2a 登记、扩表时必须连读的偏差**（见 `ai_docs/SESSION_HANDOFF.md` 队列第 13 条）：
  a) `findFeaturePosition` 的 `MF_NEAR_ORIGIN` 以 `center` 为基准，CE 以 `originX/originY`（`Architect.c:1337-1348`）—— 对**全部 BP_ROOM 机器**都是偏差；
  b) `Architect.trapVaults` 只声明、从未 push，`Game.ts:1228` 的宝藏循环是死代码，而前厅 center 豁免掉「可通行」检查的安全性**正建立在这条死代码上**。
  这两条都要在拆轮建议里安排位置。
