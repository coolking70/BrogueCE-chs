## 一、最容易误解的项目语义

### 1.1 `damage` 字段是掷骰记法，不是 min-max

`weapons.json` / `monsters.json` 的 `damage` 是字符串，由
`CombatSystem.parseDamageString`（`src/engine/Combat/Combat.ts`）解析：

    "XdY"    →  { min: X,     max: X * Y,     clumping: X }
    "XdY+Z"  →  { min: X + Z, max: X * Y + Z, clumping: X }

**`"2d4"` 表示 2~8，不是 2~4。**

CE 侧的 `damage` 是 `randomRange {min, max, clumpFactor}`，`{2,4,1}` 就是字面的 2~4。
把 CE 的 `{min,max}` 写成 `"MINdMAX"` 是**历史上真实发生过的错误**，
曾导致 43/67 只怪物伤害被放大平均 4.4 倍、最高 17 倍（dragon 25-1250 应为 25-50）。

**表达 CE 的 `{min, max}` 且 clumping=1 时，用 `"1dN+M"`**：
`N = max − min + 1`，`M = min − 1`。例：CE `{9,13}` → `"1d5+8"`。

> 比对 web 与 CE 的伤害时，**必须先用 `parseDamageString` 解析**，
> 不要对字符串做正则取数，也不要按字面把 `XdY` 读成 X~Y。

### 1.2 护甲值有两套标度

- CE 的 `armor` 字段是 **×10 定点**（leather = 30），显示值 = `armor/10 + enchant1`（`Items.c:1544`）
- web 的 `armors.json` 存的是**显示值**（leather = 3）
- CE 内部防御值 = `(显示值 + netEnchant) × 10`，`defenseFraction` 吃的就是这个标度

### 1.3 CE 的护甲不减伤

CE 全源码没有"护甲从伤害里扣点数"的实现。护甲只通过
`playerDefense()` → `hitProbability()` 降低被命中概率。

### 1.4 附魔一律走 `netEnchant`

武器/护甲的附魔效果、符文强度，都要用
`CombatFormulas.netEnchant(enchantment, strength, requiredStrength)`（含力量修正），
**不要直接用 `item.enchantment` 原始值**。

### 1.5 无甲不是"护甲值为 0 的护甲"

机械调用 `playerDefense(0, 0, 力量, 0)` 会因力量盈余产生**幻影防御**
（力量 12 → 防御 30）。实战对无甲**完全跳过**该公式。
任何复算防御值的地方都要复刻这个守卫。

## 二、i18n

- `src/locales/zh_CN.json` 用**扁平的带前缀键**：`"name.Golden Potion": "金色药水"`，
  不是嵌套结构。查找时用完整键名。
- `src/test/harness.ts` 的 headless 环境**故意用空 i18n 资源**，
  所有文案回退到 `defaultValue`。
  **在 harness 下看到英文是预期的 fallback，不是缺翻译的证据。**
  要验证实际显示，必须用真实 zh_CN 资源初始化 i18next。
- **新增任何 `i18next.t()` / `$t()` 调用，必须同时在 `zh_CN.json` 补键；
  `defaultValue` 只是兜底，不是"以后再说"的许可。**
  有测试把关：`src/test/p1_30_i18n_gate.test.ts` 静态扫描全部调用点
  （扫描器 `src/test/i18n_scan.ts`），缺键、死键、不可解析的动态键都会红。
  补键时保留 `{{}}` 插值变量名，并按中文语序写句（不要直译英文语序）。
- C 版遗留的死键归档在 `src/locales/zh_CN.legacy.json`（未被代码引用，
  留作查证）；主文件只保留实际生效的键。把键移回主文件前先确认
  代码真的引用它（动态键前缀 `name.*` / `menu.mode.*` / `mutation.*` 常驻主文件）。

## 四、确定性与 RNG

- ~~`Monster.ts`（约 291/293/482/484 行）与 `Creature.ts:24` 使用未播种的 `Math.random()`~~
  **——已失效（2026-09-17 由 C-4a-0 执行方指出，验收方复核确认）**：
  全引擎非测试源码中 `Math.random` **现为 0 处**，这些调用点早已改走 `rng`。
  统计类测试仍应避免对单次随机结果下严格相等断言（会因取样脆弱假红，
  B-1 与 P4-7 都栽过），但理由是**统计脆弱**，不是"未播种"。
- **同 seed 的可复现单元是"完整生成链"，不是任意中间层。**（C-4a-0 实测）
  `rng` 是全局单例，`startNewGame` 重播种，但 `generateDepth` 沿用当前流位置，
  且 web **没有 CE 的 per-level `levelSeed` 设施**（CE 用 levelSeed 隔离每层生成
  并在结束时 `restoreOldSeed`——见 P1-32）。
  后果：两个实例"各自直接跳到 D9"会得到不同结果，这是**流位置依赖，不是非确定性**。
  写确定性测试时必须走完整链（D1 逐层生成到目标层），否则会稳定假红。
- 任何改变随机数消耗顺序/次数的改动（新增抽取、改变池大小、调整发放顺序）
  都会**移动 RNG 流**，使同 seed 的地图与掉落改变。
  既有的地形指纹测试只比对"同一次运行内两次生成是否一致"，不受影响，
  但此前记录的基线表会失效——**改动若移动 RNG 流，必须在报告中说明**。

## 五、每轮任务的固定约定

### 5.1 边界

- 提示词会给出**允许修改**与**禁止触碰**的文件清单，一律严格遵守。
- 发现"该修但在边界外"的问题时：**只列入报告，不要动手**。
- **禁止执行** `git commit` / `add` / `push` / `reset` / `checkout`，改动一律留在工作区。
- 不要在仓库里创建临时文件；调试埋点用完必须移除并复核 diff。

### 5.2 测试要求

- 新增测试必须是**对抗性**的，不是确认性的：
  它要能在一个**具体的、合理的错误实现**下失败。
- 每轮至少做一次**反向验证**：人为把被测逻辑改坏，贴出测试失败的输出，然后还原。
  （历史教训：`dirs8` 方向数组漏了 `[1,1]` 却通过了"discord 生效"的测试。）
- 已有测试一律不得修改，除非提示词明确许可。

### 5.3 报告

每轮写一份 `ai_docs/<任务名>_report.md`，必须包含：

- `npm test` 与 `npm run build` 的**完整输出尾部**（不接受"已验证"的口头结论）
- `git diff --stat`
- 本轮验收条款的逐条对照
- **与预设不符之处（只列不修）** ——
  包括**提示词本身的任何错误**。这一节是刚需，不是客套。

### 5.4 授权反驳

提示词里给出的事实、行号、数字、校验和锚点，**都可能是错的**。

- 发现不符时**不要强行凑数**，如实报告你得到的结果并说明分歧出在哪里。
- 提示词的指令与 CE 源码冲突时，**以 CE 为准**，并在报告中说明。
- 提示词要求实现 CE 中不存在的机制时，**拒绝实现**并给出源码证据。

> 历史记录：这条口子被用过十余次，包括两次成功拒绝错误指令
> （CE 并无饥饿力量惩罚、Faint 不会失去回合）。若当时照做，
> 项目会一边宣称"对齐 CE"、一边凭空加进两个 CE 不存在的机制。

## 留痕测试与文件边界（2026-09-16 立，已四次踩坑）

本项目要求"明确不做的事写显式留痕测试"（断言现状，而非静默跳过）。这条很有用，
但它与"文件边界"有一个**系统性冲突**：

> **当某一轮要实现的、正是先前留痕测试所记录的"未做项"时，
> 那个留痕测试的前提就会失效，而它通常不在本轮的"允许修改"清单里。**

已经发生四次：
- P1-27 移除淹死 ↔ P1-24 的 7 条"淹死会死透"断言
- P1-31 修落位 ↔ P4-9 的 T8"出生态站在楼梯上"
- B-1 实现武器三特性 ↔ P4-7 的"这三件武器不应携带旗标"
- P1-33 清零坏层 ↔ P1-26 / P1-29 的已知坏层集

每次的表现都一样：执行方**正确地停下来申报**（因为边界禁改），验收方再补一刀。

### 规矩

**写任务书时，如果本轮要实现的东西被某个留痕测试记录着，
必须把那个测试文件列入"允许修改"，并写明"仅为反转该留痕断言"。**

反转的标准做法（B-1 那次可作范本）：
- 不是删掉，而是**改成断言新事实**，并保留一条"越界守卫"
  （例如"其余武器不得沾上这四个旗标"）；
- 测试名里把"本轮明确不做"改成"XX 已反转"，注明实现轮次；
- 注释里保留原断言内容，让后人看得懂这条是怎么演化来的。

### 写留痕测试时

**在测试名或注释里写明"哪一轮会来反转我"**，例如
"P1-29 修复后本断言应改为严格 0"。P1-26 那条做得最好：失败消息直接写了
"若不可达层数为 0，说明 P1-29 已修复：请把常量改为 0 并更新断言名"——
下一个人接手不需要回来问。

## 留痕测试必须防"改写形态绕过"（2026-09-17 立，第 6 起冲突后）

留痕测试常用**静态扫描源码**实现（"这个字段在生产代码里零读取点"、
"这个函数生产零调用点"）。它们的问题是：**扫描的是形态，不是语义。**

实例：C-4a 的 E 组留痕禁止生产代码出现 `.mechFlags`（点号读取）。
C-4b 合法地需要 `mechFlags`，但那条测试当时不在它的允许修改清单里，
于是它写成 `const { mechFlags } = entry`——**语义一模一样，正则不匹配，
测试继续绿**。执行方如实申报了，但这仍然是**自造的假绿**：
读者确实存在，断言却报"零读者"。

**规矩：**
1. **留痕若能被改写形态绕过，它就不是门禁而是装饰。** 写静态扫描时，
   至少覆盖点号读取与解构读取（含重命名 `{ a: b }`）两种形态；
   函数调用类留痕要考虑别名赋值（`const f = obj.method`）。
2. **加固之后要反向验证**：真的注入一个该形态的违规读者，确认翻红，再还原。
   （本条规矩自身就是这么验的。）
3. **宁可红，不可绕。** 遇到留痕与文件边界冲突时，正确动作是**停下来申报**
   （执行方做对了），由验收方翻转断言；**不是**把代码扭曲成正则看不见的样子。
4. 写任务书时，凡本轮会给某个留痕"接上第一个读者/调用者"的，
   **提前把那个测试文件按条目放进允许清单**。
   （这条冲突已累计 6 起，前 5 起都是任务书没提前安排。）

## 「照抄留形」的死分支不受任何测试保护（2026-09-17 立，G-2 实证）

移植 CE 时常会遇到"这条分支 web 今天没有载体"的情况。既有做法是
**照抄留形**——把 CE 的逻辑忠实写下来但标注"结构性不可达，留给某轮行使"。
这个做法本身是对的（激活轮只需接上载体），但有一个**致命的盲区**：

**写它的那一轮无法测它**（分支不可达，任何测试都进不去），
**于是抄写错误可以在库里躺很多轮而不被发现**。

实证：F-2a 写下 `Promotion.ts` 的 `ALL_DIRS8` 时把 `[1,-1]` 抄了两次、
漏了 `[1,1]`（CE `GlobalsBase.c:38` 的 `nbDirs` 是八个互不相同的方向）。
它只被爆轰分支 `TM_EXPLOSIVE_PROMOTE` 使用，而 web 当时没有该旗标的载体——
**错抄安然躺过 F-2a、F-2b、G-1 三轮**，直到 G-2 接上甲烷载体才暴露。
（幸而火焰蔓延走的是 4 正交邻，没被污染。）

**规矩**：
1. **激活留形分支的那一轮，必须逐字符重核 CE**，不要因为"它已经在库里躺了几轮"
   就信任它；
2. 写留形代码时，**能用测试固定的部分就固定**——例如方向表这类纯数据，
   即使分支不可达，也可以直接断言表的内容等于 CE 原值；
3. 报告里标注"结构性不可达"时，**同时标注"激活轮需重核"**。

## 写"允许修改"清单前，先 grep 出真实路径（2026-09-17 立，连续两轮踩同一个坑）

「留痕授权清单」解决的是**测试文件**漏授权；但连续两轮暴露出另一半问题——
**生产文件也会漏，而且根因不同：范围写对了，文件路径靠猜。**

- **C-5**：范围里明写了 P1-22 下坠药水，那必然要加 `DF_HOLE_POTION` 条目，
  但清单没有 `DungeonFeatureCatalog.ts`；
- **B-1a**：范围里明写了"修 `DetailGenerator` 的信息泄露"（B-0 已定位），
  清单却写成"`src/components/` 下详情面板相关"——它实际在 `src/engine/UI/`。

两次都不是执行方越界，是验收方的清单与自己写的范围对不上。

**规矩：写清单前，对范围里点名的每个东西 grep 出它的真实位置。**

```bash
# 例：范围提到 DetailGenerator 与 identifiedItems
grep -rln "DetailGenerator\|identifiedItems" src/ | grep -v "^src/test/"
# 例：范围提到"接某条 DF 链"
#   → DungeonFeatureCatalog.ts / DungeonFeature.ts 默认进清单
```

**两条默认规则**（免得每次都想）：
1. 凡范围含"**接某条 DF / 地形 / 机制链**"的，
   `DungeonFeatureCatalog.ts` + `DungeonFeature.ts` + `TerrainCatalog.ts` 默认进清单；
2. 凡范围含"**修某处显示 / 泄露**"的，先 grep 出承载那处显示的文件，
   不要按目录习惯猜（web 的 UI 代码分散在 `src/engine/UI/` 与 `src/components/` 两处）。


## 漏授权的第三种形态：删除类改动要 grep「被删的公开名」（2026-09-17 B-1b 实证）

到 B-1b 为止，"任务书授权清单漏了文件"已出现**三种不同形态**，
每种的 grep 关键词不同，缺一不可：

| 形态 | 漏的是什么 | grep 什么 |
|---|---|---|
| ① 结构性穷尽表 | 钉死全量表的**测试** | `TERRAIN_FLAGS\|DRAW_PRIORITY\|TERRAIN_HOME_LAYER\|DUNGEON_FEATURE_CATALOG\|DF_MISSING_TILES\|toEqual({` |
| ② 生产文件真实路径 | 范围点名的东西**实际在哪个文件** | 范围里点名的每个符号（`DetailGenerator`、`identifiedItems`…） |
| ③ **被删符号的引用者** | 谁在用**将被删除**的公开名 | **被删的公开名本身** |

**③ 的实证**：B-1b 被要求按 D2 删除 `rechargeArcanaItem` / `uncurseItem`
两个 web 自创的免费按钮。`p1_37` 的 AD5a **把这两个方法当载体**去断言
i18n 文案渲染成中文——它既不在结构性穷尽表里，主题词也对不上
（它的主题是"机器旗标与 i18n"，不是"鉴定"）。两段 grep 双双落空。

**规矩**：凡本轮范围含"删除/重命名某个公开符号"，
**必须额外 grep 那个符号名本身**，把所有引用者放进允许清单：

```bash
grep -rn "rechargeArcanaItem\|uncurseItem" src/ | grep -v "^src/engine/Core/Game.ts"
```

**并且要预判"载体式引用"**：测试可能只是**借用**某个方法去测别的东西
（如 AD5a 借它测 i18n），这类引用者从主题上完全看不出来。

## `generation_baseline` 对「交互期掷骰」是盲的（2026-09-17 B-1c 实证）

多轮任务书用过这条硬门禁：**"本轮不许移动 RNG 流 → `generation_baseline` 必须保持绿"**
（B-1a / B-1b / B-1c 都有）。**这条门禁只覆盖生成期，对交互期是盲的。**

`generation_baseline` 的口径是"建局 + 逐层 `generateDepth`"——
它根本不推进回合。所以**任何只在玩家行动/回合结算里多消耗的掷骰，
它一概看不见**。

**实证**：B-1c 做反向验证时，往交互期注入了一次额外掷骰，
`generation_baseline` **全程是绿的**；它的哨兵初版也没翻红
（哨兵调错了函数层，漏掉真正的函数体）——**两道防线同时失效**。
是执行方自己在反向验证里发现的。

**规矩**：
1. **"不许移动 RNG 流"必须分开说**：生成期用 `generation_baseline`，
   **交互期必须另立哨兵**——用 B-1b 验证过的
   `rng.randomNumbersGenerated` **增量**口径（建在构造场景上，对流位移免疫）。
2. 立交互期哨兵时，**反向验证必须真的往交互期注入一次掷骰**，
   确认它翻红。B-1c 正是靠这一步发现自己的哨兵调错了层。
3. 任务书里写"本轮不许移动 RNG 流"时，**要指明是哪一期**，
   并给出对应的判据文件；只写 `generation_baseline` 是不够的。

## 漏授权的第四种形态：跨轮公共目录被主题测试钉死（B-3，2026-09-17）

前三种形态（结构性穷举表 / 生产文件真实路径 / 被删的公开名）已记在上面。
B-3 又漏了两条，机理是**同一种新形态**：

- `c_4c_promotion.test.ts` 钉「全库负 `promoteChance` 载体必须是且仅是这几条」
  —— B-3 新增 `FORCEFIELD:-200` / `FORCEFIELD_MELT:-10000`，撞红；
- `g_2_gas_df_wiring.test.ts` 钉 `DF_MISSING_TILES` 恰 6 条
  —— B-3 的 `DF_SHATTERING_SPELL` 缺 `RUBBLE` tile 入列，6→7，撞红。

**为什么两段 grep 抓不到**：这两个断言**扫的是全库公共目录**，
但它们所在的**文件名是按主题起的**（promotion / gas）。
按本轮主题关键词（scroll / negation / sanctuary / shatter）grep，
永远搜不到「气体接线测试」里那条 DF 名单守卫。

**根因**：公共目录是**跨轮共享的**，而钉它的断言是**按主题分散存放的**。
两者的命名空间不重合，所以主题 grep 必然漏。

### 对策：写授权清单时加**第三段 grep —— 按目录标识符搜，不按主题搜**

本轮凡是**往任何公共目录里加条目**（地形、DF、光照、层归属、绘制优先级……），
就把该目录的**标识符**本身拿去 grep 整个测试树：

```bash
for sym in TERRAIN_FLAGS DUNGEON_FEATURE_CATALOG DF_MISSING_TILES \
           LIGHT_CATALOG TERRAIN_HOME_LAYER DRAW_PRIORITY; do
  echo "== $sym =="; grep -rl "\b$sym\b" src/test --include="*.test.ts"
done
```

2026-09-17 实测的引用面（**远比直觉宽**）：

| 公共目录 | 被几个测试文件钉 | 其中"主题完全不相干"的 |
|---|---|---|
| `TERRAIN_FLAGS` | **7** | `g_3_gas_effects`、`p1_42_secret_door_search`、`c_4c_promotion` |
| `DUNGEON_FEATURE_CATALOG` | 4 | `f_2a_fire_mechanics`、`g_2_gas_df_wiring` |
| `TERRAIN_HOME_LAYER` | 4 | `f_1_fire_as_terrain`、`g_2_gas_df_wiring` |
| `DRAW_PRIORITY` | 4 | `f_1_fire_as_terrain`、`c_4b_dungeon_feature` |
| `DF_MISSING_TILES` | 2 | `g_2_gas_df_wiring` |

**加一个地形 = 至少要看 7 个测试文件**，这个数字应该成为写任务书时的默认预期。

### 撞红后怎么修：守卫要**顺延，不要放宽**

这两条守卫的原意都是「挡住有人塞进非 CE 的东西 / 顺手删掉登记」。
正确修法是**把新条目按 CE 原值补进期望值、继续全等钉死**，
而不是改成 `toBeGreaterThan` 或删掉断言。B-3 的两处都按此修：
`negative` 仍全等钉四条、`DF_MISSING_TILES` 仍全等钉长度。

**放宽守卫是把债转移给下一轮**，和硬填哨兵数值是同一种错误。

## 「挑 seed 的测试」：一种只有移动 RNG 流时才会暴露的假保证（B-4a，2026-09-18）

B-4a 是纯物品生成轮，**AI 与气味代码零改动**，却撞红了 `p4_8_scent_map` 的 T5
（追踪怪顺气味贴脸）。查下来不是回归，而是**这条测试从一开始就靠挑 seed 才过**：

| 跑法 | 结果 |
|---|---|
| main 上把同一场景跑 12 个不同 seed | **1 个成功**（正是原版用的默认 seed）|
| B-4a 上跑 40 个 seed | **5 个成功（12.5%）** |
| main 上只加一句「建场后重播种」、其余不改 | **同样翻红** |

两边成功率统计一致（约 10%），所以 B-4a 没改变任何行为，
**只是把流位置挪开了那颗走运的骰子**。

### 危害

这类测试**看起来是行为断言，实际是快照**。它给出的信心是假的：
T5 号称「下坡/原地/弃味实现皆败」，但**正确实现也有约 90% 的概率失败**。
于是它既挡不住真缺陷，又会在每个移动 RNG 流的轮次里制造假红，
消耗验收方大量时间去排查一个并不存在的回归。

### 识别方法（**移动 RNG 流的轮次撞红时，第一件事**）

不要先怀疑本轮改动，先问**「这条测试在别的 seed 上过不过」**：

```ts
// 把场景包进 for 循环跑 20-40 个 seed，统计成功率
// 成功率 ≈ 100% → 真回归，去查本轮改动
// 成功率  ≈ 10% → 挑 seed 的假保证，问题在测试本身
```

判据：**同一场景在 main 与本轮分支上的成功率是否统计一致**。
一致 = 本轮无辜；本轮显著更低 = 真回归。

### 处置

1. **不要靠重新挑一个能过的 seed 了事就完** —— 那只是把债推给下一个生成轮；
   但在无法当轮查清根因时，**钉一个显式 seed 恢复原有保证是可接受的临时处置**，
   前提是③做到。
2. **补一条与 seed 无关的性质断言**。T5 补的是「前后都仍是 HUNTING 的那一步，
   必须气味严格上坡」——它在两边的全部 seed 上都绿，是真正能挡住
   「下坡/argmin 实现」的那条线。
   注意取样时序：CE 的 3% 丢目标（`Monsters.c:1674-1680`）发生在**回合内的
   状态更新阶段、先于移动**，所以只看回合开始时的状态会误判——
   必须**前后都是 HUNTING** 才算「追踪态下的移动」。
3. **把根因登记成未决项**，并在测试注释里**明写"结局断言不构成行为正确的证据"**，
   免得下一个人再把它当成保证。

### 顺带：`tsc --noEmit` 不是本项目的类型门禁

同日发现：验收一直用 `npx tsc --noEmit`，它解析根 `tsconfig.json`，
而 `noUnusedLocals` / `noUnusedParameters` 写在 `tsconfig.app.json` 里，
**只有 `npm run build`（`vue-tsc -b`）才应用**。
B-3 因此把一个 TS6133 放进了 main。**门禁一律以 `npm run build` 为准。**
