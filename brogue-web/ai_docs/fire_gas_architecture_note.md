# 火与气体：web 自创子系统 vs CE 的地形驱动（C-4c 暴露，待用户裁决）

> 验收方写于 2026-09-17 凌晨，P1-42 执行期间。
> **这不是任务书能决定的事**，按 D3（大改先出方案文档再动手）先写清楚。

---

## 一、C-4c 把这个问题顶到了台面上

C-4c 把 `promoteTile` 与每回合两趟驱动接上之后，实测结论里有两条刺眼的：

- **`fireType` 轴整体休眠**——CE 里每个可燃地形都有 `fireType`（烧起来变成什么），
  是火焰蔓延的唯一机制。web 的火完全不走这条轴，走的是 `cell.isBurning` 布尔位
  （全库 33 处非测试引用）+ `Gas.ts` 的 `GasType.FIRE`。
- **C-4b 登记的 11 个缺失地形里，7 个是火与气体**：`PLAIN_FIRE`、`EMBERS`、
  `BRIMSTONE_FIRE`、`ACTIVE_BRIMSTONE`、`STEAM`、`METHANE_GAS`、`POISON_GAS`。
  它们缺席不是疏漏——**web 根本没有"火焰是一种地形"这个概念**。

结果是：**硫矿湖每回合掷 11 次骰，100% 缓办，地形零变化。**
C-4 那一整条链（属性表 → DF 目录 → promoteTile → 两趟驱动）在火与气体这一半上
是空转的。

---

## 二、两边的架构差在哪

| | CE | web |
|---|---|---|
| 火焰 | **是地形**：`PLAIN_FIRE` / `BRIMSTONE_FIRE` / `GAS_FIRE` 等 10 种带 `T_IS_FIRE` 的 tile，活在 SURFACE 层 | `cell.isBurning` 布尔 + `burnDuration`，外加 `GasType.FIRE`（**已知死枚举**） |
| 蔓延 | 每个可燃 tile 的 `fireType` 字段 + `chanceToIgnite` + `exposeTileToFire` | `environment.ignite()` 的硬编码白名单（草/植被/沼泽/门） |
| 气体 | **是地形**：GAS 层 + `pmap.volume`；DF 目录里 **24 条**写入 GAS 层；扩散靠 `updateVolumetricMedia`（每回合跑**两次**，`Time.c:1615-1616`） | `Gas.ts` 独立网格：`GasType` 六值枚举 + `density` 0-100，288 行自有实现 |
| 与地形的耦合 | 完全统一：气体、火、液体、地板都是 tile，共用 drawPriority / flags / promote | 三套并行：`terrain` 四层（C-4a-0 后）、`isBurning` 布尔、`Gas.ts` 网格 |

**web 的 `GasType` 只有 6 值，CE 的 GAS 层 DF 有 24 条。**
而且 C-4a-0 迁入的四层模型里，**GAS 层至今恒空**——留痕测试钉着它。
那一层是给 CE 的气体准备的，web 的气体却住在别处。

## 三、三条路

### 路线 A：把火与气体也迁成地形（全量对齐 CE）

- 新增 `T_IS_FIRE` 系与 GAS 层地形，`Gas.ts` 的职责移交给 `promoteTile` +
  `spawnDungeonFeature` + `updateVolumetricMedia` 的移植；
- `isBurning` 布尔退役（33 处引用改查 `T_IS_FIRE`）；
- GAS 层从"恒空"变成活的，C-4a-0 那条留痕翻转。

**代价**：这是 Phase C 里最大的单项改动，且**必然改变玩法**
（火焰蔓延规则、气体扩散速度、中毒/迷惑的判定点全变）。
**收益**：C-4 链的另一半激活；硫矿、蒸汽、沼气、毒气链自动接通；
此后新增的任何 CE 地形都不需要再做架构决策。

### 路线 B：保留 `Gas.ts`，只补火焰地形

只做 `T_IS_FIRE` 系，气体仍走 `Gas.ts`。
**代价**：GAS 层继续恒空，CE 的 24 条 GAS 层 DF 永远接不上；
`DF_STEAM_ACCUMULATION`（深水的 fireType）这类横跨火与气体的链会断在中间。
**这条路会留下一个说不清的边界**，不推荐。

### 路线 C：维持现状，把 7 个火/气体地形永久登记为"不实现"

**代价**：承认 C-4 链有一半是装饰；硫矿湖永远点不着（C-2 那笔欠账变成坏账）；
`fireType` 字段全库无读者。
**好处**：零风险，且 web 现有的火/气体玩法是能跑的。

## 四、验收方的意见

**倾向 A，但要拆成三轮，且必须先有一轮纯测量。**

理由：这和 C-4 那次的教训一模一样——C-4 原样投不出去，是因为它预设了
不存在的底座；现在如果直接投"迁移火与气体"，执行方会面对
"33 处 `isBurning` 引用 + 288 行 `Gas.ts` + 24 条 GAS 层 DF"三线同时开工，
一样无法验收。

建议拆法（沿用已验证两次的「结构先行 + 完美门禁」模式）：

1. **F-0（纯测量，不改行为）**：量清 `isBurning` 的 33 处引用各自在问什么、
   `Gas.ts` 的哪些行为有 CE 对应物、哪些是自创（D2 口径）；
   产出一张"CE 机制 ↔ web 现实现"的逐条对照表。
   **这一轮的产出是决策依据，不是代码。**
2. **F-1（火焰迁成地形，行为逐位不变）**：新增 `T_IS_FIRE` 系地形与 DF，
   `isBurning` 改为**派生自**地形（而不是并列的事实来源），
   蔓延规则暂时仍走旧白名单——门禁是"行为逐位不变"。
3. **F-2（放开 CE 的蔓延规则）**：`fireType` + `chanceToIgnite` 生效，
   旧白名单退役。**这一轮真改玩法**，判据是实测影响报告。
4. 气体同理再走一遍（G-0/G-1/G-2），或在 F-0 的结论里合并。

**但这条路值不值得走，取决于用户对"还原度 vs 现有玩法稳定性"的取舍——
所以先问。**
