# i18n 结构性风险评估

> 2026-09-16。起因：项目负责人指出 C 版的汉化是在 CE（本身无本地化支持）上后加的，
> 执行不完善、结构性问题未解决，询问 JS 重构版是否存在同类风险。
> 本文全部结论均为**实测**，不是静态推断。

---

## 结论先行

**架构上，web 版比 C 版更健康；流程上，有一个正在持续恶化的漏洞。**

C 版的病根是**翻译已拼装的句子**——`templateMatch` 拿英文成句去匹配模板、再回填捕获值，于是有了 `strstr` 越界、COLOR_ESCAPE 字节被误判成 `%`、多占位符模板全数失配那一串问题（详见项目记忆里第三至第八轮的修复史）。

web 版**没有继承这个病根**：它用 i18next 的「键 + 插值」模型，`t('combat.hit', { monster, damage })`，句子结构在翻译文件里、变量单独传入。**这是正确的架构，不需要模板匹配，也就不会有 C 版那一类 bug。**

但它有另一个问题：**`defaultValue` 让缺失翻译完全静默**。

---

## 一、实测数据

```
翻译文件总键数     : 2805
代码实际引用的键   : 281
  其中命中         : 221
  其中缺失         : 60   ← 21% 的调用点落到英文
翻译文件中从未被用 : 2584 (92.1%)
  含 printf 占位符（C 版遗留，JS 永不可能命中）: 592
```

### 1.1 缺失的 60 个键会渲染成什么

实跑 `i18next.t()` 的真实输出：

```
combat.monster_splits     存在=false  渲染="The 粉色果冻 splits in two!"
combat.monster_seizes_you 存在=false  渲染="The 沼泽怪 seizes your legs!"
death.bloat_gas           存在=false  渲染="The 膨胀怪 releases a cloud of caustic gas!"
combat.monster_kamikaze   存在=false  渲染="The 膨胀怪 lunges at you and bursts!"
combat.backstab           存在=false  渲染="You backstab the 老鼠 for 7 damage!"
env.monster_drowns        存在=false  渲染="The 老鼠 drowns."
```

**中文名嵌在英文句子里——两头不靠。** 比纯英文更糟，因为它看起来像"翻译坏了"而不是"还没翻译"。

### 1.2 这 60 个键绝大多数是最近几轮新加的

`combat.monster_splits`（P4-4）、`combat.monster_seizes_you`（P4-5）、`death.bloat_gas`（P4-4）、`combat.ally_kamikaze`（P4-4）、`combat.discordant_seizes`（P4-5）……

**这说明漏洞在持续扩大：每加一轮功能就多几条英文。** 因为 `defaultValue` 不报错、不告警、测试也不检查，没有任何机制会让人注意到。

### 1.3 变异名完全没翻译

```
explosive  变异后的怪物名 = "explosive 老鼠"
infested   变异后的怪物名 = "infested 老鼠"
agile      变异后的怪物名 = "agile 老鼠"
juggernaut 变异后的怪物名 = "juggernaut 老鼠"
```

`Monster.ts:402` 的 `this.name = m.name + ' ' + this.name` 直接拼接未翻译的变异名。8 个变异全部如此。

顺带一提，这里还有个**语序问题**：中文不该是"explosive 老鼠"，形容词与名词的组合方式需要单独的键（例如 `mutation.explosive` → `"爆裂的"` 再拼成 `"爆裂的老鼠"`），不能靠简单拼接——这正是 C 版栽过的那类坑。

---

## 二、做对了的部分（不要动）

- **怪物名 67/67 全部有翻译**，且在 `Monster` 构造时统一经 `ItemLoader.translateName`（`Monster.ts:291`）翻译，不是在每个使用点各翻一次。
- **物品名走同一条路**（`ItemLoader.translateName`），药水/卷轴的随机外观名也接了。
- **没有模板匹配**。这是与 C 版最本质的区别，务必保持——将来**不要**为了省事引入"拿英文句子反查翻译"的机制。

---

## 三、翻译文件本身：92% 是死数据

`zh_CN.json` 是**从 C 版整体继承过来的**，2805 个键里 2584 个（92.1%）代码从未引用：

- **1564 个无点号键**是 C 版的原文键，内容包括命令行帮助文本、`****` 标记的菜单串等，与 web 完全无关。
- **592 个含 `%s` / `%i`** 是 C 的 printf 约定。i18next 用 `{{}}`，**这些键永远不可能命中**。
- 只有 **109 个键使用 `{{}}` 插值**——那是真正为 web 写的。

死数据本身不致命（只是 229KB 的包体与检索噪音），但它制造了一种**虚假的丰盈感**：文件看着有 2805 条翻译，实际生效的只有 221 条。评估覆盖率时极易被误导。

---

## 四、风险定级

| 风险 | 严重度 | 说明 |
|---|---|---|
| **缺失键静默回落英文** | **高** | 玩家可见；且随每轮开发持续恶化 |
| 变异名未翻译 + 语序错误 | 中 | 玩家可见，但变异怪出现频率较低 |
| 92% 死键 | 低 | 不影响正确性，影响包体与可维护性 |
| 引入模板匹配的诱惑 | **潜在高** | 一旦有人为省事这么做，C 版的全部病症会重演 |

---

## 五、建议的修法（按性价比排序）

### 5.1 立刻做：把静默漏洞变成红灯（成本极低，收益最大）

新增一条测试：**扫描源码里所有 `t()` 调用的键，断言每个键都存在于 `zh_CN.json`**。

- 这是**机制性修复**：从此任何人加一条新消息忘了加翻译，CI 立刻红。
- 与本项目"每条断言都要能在具体错误实现下失败"的纪律一致。
- 实现只需十几行（我评估时已经写过一版扫描脚本，可直接改造）。

**没有这一条，其余修复都会在几轮之后重新腐化。**

### 5.2 随后：补齐 60 个缺失键 + 8 个变异名

变异名要按中文语序设计键（形容词单独成键，拼接规则单独处理），不要照搬英文的 `形容词 + 名词` 拼法。

### 5.3 可选：清理死键

把 2584 个未引用键移出主文件（或归档为 `zh_CN.legacy.json` 备查）。这能让"翻译覆盖率"这个指标恢复意义。
**注意**：清理前应确认 C 版汉化工作是否还需要复用这份文件——若两边共用，则只做归档不做删除。

### 5.4 写进 `project_conventions.md`

加一条：**新增任何 `i18next.t()` 调用，必须同时在 `zh_CN.json` 补键**；`defaultValue` 只作为兜底，不是"以后再说"的许可。

---

## 六、给项目负责人的一句话总结

C 版那些结构性问题（模板匹配、占位符错配、颜色字节干扰）**在 web 版不存在，也不会重演**——只要不引入"反查英文句子"的机制。

web 版真正的风险是**流程性的**：`defaultValue` 提供了一条无声的降级通道，于是每轮开发都在悄悄积累英文残留，目前已达 21%。这个问题用一条测试就能永久堵住，**建议优先于任何补翻译的工作先做**。
